13-1. 설계 문제 접근 틀 🔥 ✍️

단계할 일시간 배분 (45분 기준)
1. 요구 사항 명확화기능 범위, 사용자 규모, 읽기/쓰기 비율, 일관성·지연·가용성 요구를 질문5분
2. 규모 추정QPS, 저장 용량, 대역폭5분
3. API · 데이터 모델핵심 API 몇 개, 주요 테이블과 키5~10분
4. 고수준 설계구성 요소와 데이터 흐름을 그림으로10분
5. 상세 설계가장 어려운 부분 한두 곳을 깊게10분
6. 병목 · 장애 · 확장단일 장애점, 핫스팟, 모니터링, 향후 확장5분

기능 요구와 비기능 요구를 나눠 적는다

비기능 요구묻는 것설계에 주는 영향
규모사용자·데이터·요청이 얼마인가단일 서버로 되는가, 분산이 필요한가
읽기 : 쓰기 비율읽기 위주인가 쓰기 위주인가캐시·복제본 vs 샤딩·큐
일관성조금 오래된 값을 보여도 되는가강한 일관성 vs 결과적 일관성
지연 시간얼마나 빨라야 하는가캐시, CDN, 비동기 처리
가용성중단을 얼마나 허용하는가이중화, 다중 영역
내구성데이터를 잃어도 되는가복제, 백업, 동기 쓰기

흔한 실수: 요구 사항을 묻지 않고 바로 그리기, 필요 없는 구성 요소를 처음부터 넣기, 선택의 대가를 말하지 않기. 단순하게 시작해서 병목이 드러나는 곳만 복잡하게 만든다.

13-2. 규모 추정 🔥 🧮

외워 둘 수

2의 거듭제곱값단위
2¹⁰약 1천KB
2²⁰약 100만MB
2³⁰약 10억GB
2⁴⁰약 1조TB
  • 하루 = 86,400초 ≈ 10⁵ 초. 하루 100만 건 ≈ 초당 12건, 하루 1억 건 ≈ 초당 1,200건.
  • 최대 부하는 평균의 2~10배로 잡는다.
동작대략의 시간
L1 캐시 참조1 ns
메모리 참조100 ns
SSD 임의 읽기100 μs
같은 데이터센터 안 왕복0.5 ms
디스크(HDD) 탐색10 ms
대륙 간 왕복150 ms

교훈: 메모리는 디스크보다 수천 배 이상 빠르고, 네트워크 왕복은 생각보다 비싸다. 그래서 캐시를 쓰고, 여러 번 왕복할 것을 묶어서(배치) 보낸다.

예제. 일간 활성 사용자 1,000만 명, 1인당 하루 글 2개 작성(평균 1KB), 조회 20회. 쓰기·읽기 QPS 와 5년간 저장 용량은?

풀이
  • 쓰기: 1,000만 × 2 = 2,000만 건/일 → 2×10⁷ / 10⁵ ≈ 200 QPS (최대 약 1,000)
  • 읽기: 1,000만 × 20 = 2억 건/일 → 2×10⁸ / 10⁵ ≈ 2,000 QPS (최대 약 10,000)
  • 읽기 : 쓰기 = 10 : 1 → 읽기 위주 → 캐시와 읽기 복제본이 효과적
  • 저장: 2,000만 × 1KB = 20GB/일 → 연 7.3TB → 5년 약 37TB (복제 3벌이면 약 110TB)
  • 결론: 단일 DB 한 대로는 저장 용량이 부족하므로 샤딩 또는 분산 저장소를 검토한다.

13-3. 확장성 기본기 🔥

수직 확장 vs 수평 확장

구분수직 확장 (Scale-up)수평 확장 (Scale-out)
방법서버 사양을 높임서버 대수를 늘림
장점단순, 애플리케이션 변경 없음한계가 높음, 장애 내성, 비용 효율
단점물리적 한계, 비쌈, 단일 장애점분산의 복잡성 (데이터 일관성, 세션, 배포)
적합초기, 관계형 DB 의 쓰기무상태 애플리케이션 서버

무상태 서버

수평 확장의 전제. 서버가 세션·파일 같은 상태를 자기 안에 두지 않으면 어떤 요청이 어떤 서버로 가도 된다.

상태옮길 곳
로그인 세션Redis 같은 공유 저장소, 또는 토큰(JWT)
업로드 파일객체 저장소
캐시분산 캐시
예약 작업분산 스케줄러 (중복 실행 방지)

전형적인 발전 단계

  1. 서버 한 대에 웹 + DB
  2. DB 를 분리 (각자 확장)
  3. 애플리케이션 서버 여러 대 + 로드 밸런서 (→ L4 vs L7), 서버를 무상태로
  4. DB 읽기 복제본 + 캐시 (읽기 부하 해소)
  5. 정적 콘텐츠를 CDN 으로
  6. 오래 걸리는 일을 메시지 큐로 비동기 처리
  7. DB 샤딩, 서비스 분리(MSA)
  8. 다중 데이터센터

각 단계는 직전 단계의 병목을 푼다. 문제가 없는데 다음 단계로 가면 복잡도만 늘어난다.

단일 장애점 제거

구성방식특징
Active-Standby한 대가 서비스, 다른 한 대는 대기하다 장애 시 승계전환 시간 존재, 대기 자원 유휴
Active-Active여러 대가 동시에 서비스자원 효율, 데이터 동기화·충돌 처리 필요
  • 이중화했다면 장애 조치를 실제로 해 봐야 한다. 전환이 안 되는 이중화가 흔하다.

13-4. 분산 데이터 — 복제 · 샤딩 · 일관성 해싱 🔥 🧮

복제·파티셔닝·샤딩의 기본 정의는 → 복제 · 파티셔닝 · 샤딩

복제 구조

구조쓰기특징
단일 리더리더 한 대만단순, 충돌 없음. 리더가 쓰기 병목·장애점
다중 리더여러 리더지역별 쓰기 가능. 쓰기 충돌 해결 필요
리더 없음아무 노드나고가용. 정족수(쿼럼) 로 일관성 조절 (Dynamo, Cassandra)

정족수 (Quorum)

복제본 N 개, 쓰기 성공 기준 W 개, 읽기 기준 R 개일 때 W + R > N 이면 읽기 집합과 쓰기 집합이 반드시 겹쳐 최신 값을 적어도 하나 읽는다.

예제. N = 3 일 때 (W, R) = (2, 2), (3, 1), (1, 1) 의 성질은?

풀이
설정W + R > N성질
W=2, R=24 > 3 ✅강한 일관성. 노드 1대 장애까지 읽기·쓰기 가능 (균형)
W=3, R=14 > 3 ✅읽기가 빠름. 노드 1대만 죽어도 쓰기 불가
W=1, R=12 > 3 ❌가장 빠르고 가용성 높음. 오래된 값을 읽을 수 있음 (결과적 일관성)

일관성 모델

모델보장예
강한 일관성 (선형성)쓰기가 끝나면 모든 읽기가 그 값을 봄계좌 잔액, 재고, 분산 락
내 쓰기 읽기 (Read-your-writes)내가 쓴 것은 내가 바로 봄프로필 수정 직후 화면
단조 읽기한번 본 값보다 과거 값을 다시 보지 않음새로 고침 때 글이 사라지지 않음
결과적 일관성쓰기가 멈추면 언젠가 모두 같아짐좋아요 수, 조회 수, DNS

샤드 키와 분할 방식

방식장점단점
범위 기반범위 조회에 유리특정 범위에 쏠림 (최신 데이터 샤드만 뜨거움)
해시 기반고르게 분산범위 조회 불가, 샤드 수 변경 시 대이동
디렉터리 기반매핑표로 유연하게매핑 저장소가 병목·장애점

좋은 샤드 키: 값이 다양하고(카디널리티), 고르게 분포하며, 대부분의 조회가 샤드 하나에서 끝나도록 한다. 유명인 계정처럼 한 키에 트래픽이 몰리는 핫 키는 따로 다룬다.

일관성 해싱 (Consistent Hashing)

hash(key) % N 방식은 서버가 하나만 늘거나 줄어도 거의 모든 키의 위치가 바뀐다(캐시라면 전부 미스).

              0
          ┌───●───┐          ● 서버 (해시값 위치)
       S3 ●       ● S1       ○ 키
          │   ○k1 │          키는 시계 방향으로 가다 처음 만나는 서버에 저장
          └───●───┘
              S2
  • 서버와 키를 같은 해시 링에 놓고, 키는 시계 방향으로 처음 만나는 서버가 맡는다.
  • 서버를 추가·제거하면 그 서버의 이웃 구간만 이동한다. 평균 K/N 개의 키만 재배치된다(K = 키 수, N = 서버 수).
  • 가상 노드: 서버 하나를 링의 여러 지점에 놓는다. 서버 수가 적을 때의 분포 불균형을 줄이고, 서버 제거 시 부하가 한 서버에 몰리지 않게 한다.
  • 쓰임: 분산 캐시, Cassandra·DynamoDB 의 파티셔닝, 로드 밸런서.

전역 유일 ID

방식장점단점
DB 자동 증가단순, 정렬 가능샤딩하면 충돌, 단일 장애점
UUID v4조율 없이 어디서나 생성128비트로 큼, 정렬 불가 → 인덱스 지역성 나쁨
스노플레이크 방식시간순 정렬 가능, 64비트시계 동기화 필요
UUID v7 / ULID앞부분이 시각 → 시간순 정렬—
  • 스노플레이크 구조: 타임스탬프(41비트) + 기계 ID(10비트) + 일련번호(12비트) → 기계당 1ms 에 4,096개.

13-5. 캐시 전략 🔥

읽기·쓰기 패턴

패턴동작장점단점
Cache-Aside (Lazy Loading)애플리케이션이 캐시를 먼저 보고, 없으면 DB 에서 읽어 캐시에 저장필요한 것만 캐시, 캐시 장애에도 동작첫 요청은 미스, 불일치 가능
Read-Through캐시가 직접 DB 에서 읽어 옴애플리케이션 코드 단순캐시 계층에 로딩 로직 필요
Write-Through쓸 때 캐시와 DB 를 함께 갱신항상 최신쓰기 지연, 읽히지 않을 데이터도 캐시
Write-Behind (Write-Back)캐시에만 쓰고 DB 반영은 나중에 모아서쓰기가 매우 빠름캐시 장애 시 유실

Cache-Aside 의 쓰기: DB 를 갱신한 뒤 캐시를 삭제한다(갱신하지 않는다). 갱신으로 하면 두 쓰기의 순서가 엇갈려 옛 값이 남을 수 있다. 삭제해도 드물게 불일치가 생길 수 있으므로 TTL 을 안전망으로 둔다.

캐시가 일으키는 장애

문제상황대책
캐시 관통 (Penetration)존재하지 않는 키를 계속 조회 → 매번 DB 로"없음"도 짧게 캐시, 블룸 필터로 사전 차단, 입력 검증
캐시 스탬피드 (Breakdown)인기 키 하나가 만료되는 순간 수많은 요청이 동시에 DB 로락을 잡은 하나만 재생성, 만료 전 미리 갱신, 만료 없는 논리적 TTL
캐시 눈사태 (Avalanche)많은 키가 동시에 만료되거나 캐시 서버가 죽음TTL 에 무작위 값을 더함, 캐시 이중화, 서킷 브레이커·속도 제한
핫 키특정 키에 트래픽 집중로컬 캐시와 2단 구성, 키 복제
큰 값수 MB 짜리 값이 단일 스레드 캐시를 막음쪼개거나 압축

축출 정책과 캐시 위치

정책버리는 대상
LRU가장 오래 사용하지 않은 것
LFU사용 횟수가 가장 적은 것
FIFO가장 먼저 들어온 것
TTL수명이 다한 것
위치예특징
브라우저 · CDNHTTP 캐시서버에 요청 자체가 오지 않음
로컬 캐시Caffeine가장 빠름. 서버마다 값이 달라질 수 있음
분산 캐시Redis, Memcached서버들이 공유. 네트워크 왕복 비용
DB 내부버퍼 풀자동

캐시할 가치가 있는 것: 자주 읽히고, 드물게 바뀌고, 만드는 비용이 큰 데이터. 캐시 적중률을 측정하지 않으면 캐시가 도움이 되는지 알 수 없다.

13-6. 메시지 큐 · 이벤트 기반 구조 ⭐

왜 쓰는가

효과설명
비동기 처리메일 발송·영상 변환 같은 느린 작업을 응답 경로에서 뺀다
결합도 감소생산자는 소비자가 누구인지, 살아 있는지 몰라도 된다
부하 평탄화순간 폭주를 큐에 쌓아 두고 소비자가 감당할 속도로 처리
확장소비자를 늘려 처리량 증가
복원력소비자가 죽어도 메시지는 남아 복구 후 처리

대가: 구조가 복잡해지고, 결과적 일관성을 받아들여야 하며, 흐름 추적이 어려워진다.

용도작업 분배이벤트 전파
예SQS, RabbitMQ 큐SNS, Kafka 토픽(소비자 그룹별)

Kafka 구조

개념설명
토픽메시지의 논리적 분류
파티션토픽을 나눈 단위이자 추가만 되는 로그. 병렬 처리의 단위
오프셋파티션 안에서의 메시지 위치 번호
브로커Kafka 서버. 파티션은 여러 브로커에 복제된다

보존읽어도 지워지지 않고 기간·용량 기준으로 보존 → 다시 읽기 가능
  • 순서 보장은 파티션 안에서만 된다. 같은 키(예: 주문 ID)는 같은 파티션으로 가므로 키 단위 순서가 지켜진다.
  • 한 파티션은 그룹 안의 소비자 하나만 읽는다. 소비자를 파티션 수보다 많이 늘려도 처리량은 늘지 않는다.

전달 보장과 멱등 소비

보장의미결과
최대 한 번 (At-most-once)처리 전에 확인유실 가능, 중복 없음
최소 한 번 (At-least-once)처리 후에 확인유실 없음, 중복 가능 — 가장 흔한 선택
정확히 한 번 (Exactly-once)중복도 유실도 없음제한된 조건에서만 가능, 비용 큼

실무의 답: 최소 한 번 전달 + 멱등한 소비자. 소비자가 메시지 ID 를 기록해 이미 처리한 것은 건너뛰거나, 처리 자체를 여러 번 해도 같은 결과가 되게 만든다. → 멱등성

운영 개념내용
데드 레터 큐 (DLQ)여러 번 실패한 메시지를 따로 빼 두어 뒤의 메시지를 막지 않게 함
배압 (Backpressure)소비자가 감당 못 하면 생산 속도를 늦추거나 거절
컨슈머 랙 (Lag)생산된 위치와 소비한 위치의 차이. 핵심 모니터링 지표
재처리버그 수정 후 오프셋을 되돌려 다시 소비

13-7. 분산 트랜잭션 · 합의 ⭐

서비스마다 DB 가 다르면 하나의 로컬 트랜잭션으로 묶을 수 없다. "주문은 생성됐는데 결제는 실패" 같은 상태를 어떻게 다룰 것인가.

2단계 커밋 (2PC)

  1. 준비 단계: 조정자가 모든 참여자에게 "커밋할 수 있는가?"를 묻고, 참여자는 준비를 마친 뒤 응답한다.
  2. 커밋 단계: 모두 "예"면 커밋, 하나라도 "아니오"면 전부 롤백.
장점단점
원자성 보장 (강한 일관성)준비 후 조정자가 죽으면 참여자가 락을 쥔 채 무한 대기(블로킹)
모든 참여자가 살아 있어야 함 → 가용성 저하, 느림

사가 (Saga)

긴 트랜잭션을 로컬 트랜잭션의 연속으로 쪼개고, 중간에 실패하면 이미 끝난 단계를 보상 트랜잭션으로 되돌린다.

주문 생성 ─▶ 결제 승인 ─▶ 재고 차감 ─✗ 실패
                 ◀── 결제 취소 ◀── (보상)
   ◀── 주문 취소 ◀── (보상)
방식조율장점단점
코레오그래피각 서비스가 이벤트를 듣고 다음 일을 함느슨한 결합, 단순흐름이 흩어져 파악하기 어려움
오케스트레이션중앙 조정자가 순서를 지시흐름이 한곳에 보임조정자에 로직 집중
  • 사가는 격리성을 보장하지 않는다. 중간 상태가 밖에 보인다(결제는 됐지만 재고는 아직). 보상할 수 없는 단계(메일 발송)는 맨 뒤에 둔다.

아웃박스 패턴

"DB 에 저장하고 그리고 메시지를 발행한다"는 두 동작은 하나의 트랜잭션이 아니다. 저장 후 발행 전에 죽으면 메시지가 유실된다.

→ 업무 데이터와 발행할 메시지를 같은 DB 트랜잭션으로 아웃박스 테이블에 저장하고, 별도 프로세스(폴링 또는 CDC)가 아웃박스를 읽어 메시지 브로커로 보낸다. 최소 한 번 전달이 보장되고, 소비자는 멱등하게 만든다.

분산 락과 합의

주제내용
분산 락여러 서버 중 하나만 임계 구역에 들어가게 함. Redis SET key value NX PX 30000, 해제는 자신이 건 락인지 확인 후 삭제
락의 함정만료 시간보다 작업이 길어지면(GC 멈춤 등) 두 클라이언트가 동시에 락을 가졌다고 믿는다 → 펜싱 토큰(단조 증가 번호)으로 늦은 쓰기를 거부
합의 알고리즘여러 노드가 하나의 값·순서에 동의. Raft, Paxos. 리더 선출 + 로그 복제, 과반이 살아 있으면 동작
과반이 필요한 이유두 과반 집합은 반드시 겹친다 → 스플릿 브레인 방지. 그래서 노드를 홀수(3, 5)로 둔다
쓰임etcd, ZooKeeper, Consul — 설정 저장, 리더 선출, 서비스 발견

13-8. 장애 내성 패턴 🔥

분산 시스템에서 부분 장애는 정상 상태다. 목표는 장애가 없게 하는 것이 아니라 하나의 장애가 전체로 번지지 않게 하는 것이다.

연쇄 장애가 생기는 과정

하위 서비스 B 가 느려짐 → A 의 스레드가 B 를 기다리며 모두 묶임 → A 도 응답 불가 → A 를 부르는 서비스도 묶임 → 사용자가 재시도 → 부하 증가 → 전체 중단.

패턴동작막는 것
타임아웃정한 시간 안에 응답이 없으면 포기무한 대기로 인한 자원 고갈. 모든 외부 호출에 필수
재시도 + 지수 백오프 + 지터간격을 2배씩 늘리고 무작위 값을 더해 재시도일시적 오류. 지터가 없으면 재시도가 동시에 몰린다
서킷 브레이커실패율이 임계값을 넘으면 호출을 즉시 차단죽은 서비스에 계속 요청해 자원을 낭비하는 것
벌크헤드 (격벽)대상별로 스레드 풀·커넥션 풀을 분리한 의존성의 문제가 전체 자원을 잠식하는 것
폴백실패 시 기본값·캐시된 값·축소 기능 제공전면 실패
속도 제한일정량 이상의 요청을 거절과부하, 남용
부하 차단 (Load Shedding)과부하 시 우선순위가 낮은 요청부터 버림전체 붕괴

서킷 브레이커 상태

상태동작
닫힘 (Closed)정상 호출. 실패율을 집계
열림 (Open)호출하지 않고 즉시 실패 반환. 일정 시간 유지
반열림 (Half-Open)일부 요청만 보내 봄. 성공하면 닫힘, 실패하면 다시 열림
  • 재시도는 멱등한 요청에만, 횟수를 제한해서 한다. 여러 계층이 각자 3번씩 재시도하면 3 × 3 × 3 = 27배의 부하가 된다(재시도 폭풍).
  • 우아한 성능 저하: 추천 서비스가 죽으면 추천 영역만 비우고 주문은 계속 받는다.

속도 제한 알고리즘

알고리즘방식특징
토큰 버킷일정 속도로 토큰이 채워지고 요청마다 토큰 소비순간 폭주 허용(버킷 크기만큼). 가장 널리 사용
누출 버킷요청을 큐에 넣고 일정 속도로 내보냄출력이 균일, 폭주 불허
고정 윈도 카운터1분 단위로 개수 세기단순. 경계에서 2배 통과 가능
슬라이딩 윈도 로그요청 시각을 모두 저장정확, 메모리 사용 큼
슬라이딩 윈도 카운터이전 윈도와 현재 윈도를 가중 평균정확도와 비용의 절충
  • 서버가 여러 대면 카운터를 Redis 같은 공유 저장소에 두고, 초과 시 429 Too Many Requests 와 Retry-After 헤더를 준다.
