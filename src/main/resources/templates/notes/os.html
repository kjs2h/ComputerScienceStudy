1-1. Process vs Thread 🔥

등장 배경

초기 컴퓨터는 프로그램 하나를 통째로 올려 끝날 때까지 돌렸다(일괄 처리). CPU가 I/O를 기다리는 동안 놀았다. → 여러 프로그램을 동시에 올려 CPU를 놀리지 말자(다중 프로그래밍) → 실행 중인 프로그램을 관리할 단위가 필요 → 프로세스.

그런데 프로세스는 너무 무겁다. 하나 만들 때마다 주소 공간을 통째로 복사해야 하고, 프로세스끼리 데이터를 주고받으려면 커널을 거쳐야 한다. → 주소 공간은 공유하고 실행 흐름만 나누자 → 스레드.

핵심 정의

  • 프로세스(Process): 실행 중인 프로그램. 운영체제로부터 독립된 자원(주소 공간, 파일 디스크립터 등)을 할당받는 단위.
  • 스레드(Thread): 프로세스 내부의 실행 흐름 단위. CPU 스케줄링의 실제 대상(= dispatch 단위).

한 줄 요약: 프로세스는 자원 할당의 단위, 스레드는 CPU 실행(디스패치)의 단위. 이 한 문장이 서술 답안의 첫 줄이 되어야 한다.

왜 Stack만 따로인가? 스레드는 독립적인 함수 호출 흐름을 가진다. 함수 호출/복귀 정보(리턴 주소, 지역변수)가 섞이면 실행 흐름 자체가 붕괴한다. 그래서 독립적 실행 흐름의 최소 조건 = 자기만의 Stack + 자기만의 PC/레지스터.

동시에 이것이 Race Condition의 원인이다. Data/Heap을 공유하기 때문에 전역변수·동적 할당 객체에 여러 스레드가 동시 접근할 수 있다. → 4장 동기화로 연결.

PCB (Process Control Block) ⭐

운영체제가 프로세스를 관리하기 위해 유지하는 자료구조. 커널 영역에 존재.

담기는 정보: 1. PID (프로세스 식별자) 2. 프로세스 상태 (New/Ready/Running/Waiting/Terminated) 3. PC(Program Counter) — 다음에 실행할 명령어 주소 4. 레지스터 값들 (문맥 교환 시 저장/복원 대상) 5. CPU 스케줄링 정보 (우선순위, 큐 포인터) 6. 메모리 관리 정보 (페이지 테이블 / 세그먼트 테이블 베이스 레지스터) 7. 입출력 상태 정보 (열린 파일 목록, 할당된 I/O 장치) 8. 계정 정보 (사용한 CPU 시간 등)

프로세스 상태 전이도 ✍️

        admit              scheduler dispatch
 New ──────────► Ready ─────────────────────► Running ──── exit ──► Terminated
                   ▲                             │
                   │      interrupt (타임아웃)     │
                   └─────────────────────────────┘
                   ▲                             │
                   │                             │ I/O 또는 event 대기
                   │  I/O 또는 event 완료          ▼
                   └────────────  Waiting (Blocked)

시험 함정: Waiting → Running 직행은 불가능. 반드시 Waiting → Ready → Running을 거친다. (CPU를 받으려면 스케줄러의 선택을 받아야 하기 때문)

Context Switching (문맥 교환) 🔥

정의: CPU가 현재 실행 중인 프로세스/스레드의 상태(문맥)를 PCB에 저장하고, 다음에 실행할 프로세스의 문맥을 PCB에서 복원하여 CPU를 넘겨주는 작업.

발생 시점: 인터럽트 발생, 타임 슬라이스 만료, I/O 요청으로 Blocked 전환, 더 높은 우선순위 프로세스 도착(선점)

동작 순서

1. 인터럽트/시스템콜 발생
2. 커널 모드 전환
3. 실행 중이던 P1의 레지스터·PC를 PCB(P1)에 저장
4. 스케줄러가 다음 프로세스 P2 선택
5. PCB(P2)에서 레지스터·PC 복원
6. 사용자 모드 전환 → P2 실행 재개

Context Switching 오버헤드 — 서술 시 반드시 언급 1. 저장/복원 자체의 시간 (순수 오버헤드, 이 동안 유용한 일을 못 함) 2. 캐시 오염(Cache Pollution) — 새 프로세스가 들어오면 캐시에 남아있던 이전 프로세스 데이터가 무의미해져 캐시 미스 급증 3. TLB Flush — 프로세스마다 페이지 테이블이 다르므로 TLB를 비워야 함 (스레드 간 전환에서는 주소 공간이 같아 TLB Flush가 불필요 → 스레드 전환이 더 빠른 핵심 이유)

1-2. Interrupt / System Call ⭐

인터럽트(Interrupt)

CPU가 프로그램을 실행하는 도중 예외 상황이나 처리가 필요한 사건이 발생했을 때, 현재 작업을 중단하고 해당 사건을 먼저 처리하도록 하는 신호.

등장 배경: 폴링(Polling)—CPU가 계속 "다 됐니?"라고 물어보는 방식—은 CPU를 낭비한다. 장치가 스스로 알리게 하자.

분류 종류 예시
하드웨어 인터럽트 (외부, 비동기) I/O 인터럽트 키보드 입력, 디스크 읽기 완료
타이머 인터럽트 타임 슬라이스 만료 (선점형 스케줄링의 기반)
전원 이상 / 기계 착오
소프트웨어 인터럽트 (내부, 동기) Trap 시스템 콜(의도적)
Exception/Fault 0으로 나누기, Page Fault, 잘못된 메모리 접근

인터럽트 처리 과정 ✍️

1. 인터럽트 발생
2. 현재 실행 중인 명령어까지 완료
3. 프로그램 상태(PC, 레지스터)를 PCB/스택에 저장
4. 인터럽트 벡터 테이블 참조 → ISR(Interrupt Service Routine) 주소 획득
5. ISR 실행 (커널 모드)
6. 저장했던 상태 복원
7. 중단됐던 지점부터 실행 재개

사용자 모드 / 커널 모드 (Dual Mode) 🔥

CPU 내부의 모드 비트(Mode bit) 로 구분. 0=커널 모드, 1=사용자 모드.

사용자 모드 커널 모드
실행 가능 명령 일반 명령어만 특권 명령(Privileged Instruction) 포함 전체
접근 가능 영역 자기 프로세스 주소 공간만 모든 메모리, 하드웨어 직접 접근

왜 나누는가? 사용자 프로그램이 하드웨어를 직접 건드리면 다른 프로세스나 OS 자체를 망가뜨릴 수 있다. → 보호(Protection).

System Call ⭐

사용자 프로그램이 커널의 기능(파일 I/O, 프로세스 생성 등)을 사용하기 위해 커널에 요청하는 인터페이스. Trap을 발생시켜 커널 모드로 전환한다.

분류 예시
프로세스 제어 fork(), exec(), wait(), exit()
파일 조작 open(), read(), write(), close()
장치 관리 ioctl(), read(), write()
정보 유지 getpid(), time()
통신 pipe(), shmget(), socket()

1-3. IPC (Inter-Process Communication) ⭐

프로세스는 주소 공간이 독립적이므로 데이터를 직접 주고받을 수 없다. → 커널이 중개하는 통신 수단이 필요.

방식 설명 특징
공유 메모리(Shared Memory) 커널이 마련한 메모리 영역을 여러 프로세스가 자기 주소 공간에 매핑 가장 빠름(커널 개입은 설정 시 1회). 단, 동기화는 프로그래머 책임
메시지 패싱(Message Passing) send()/receive()로 커널을 통해 메시지 전달 느림(매번 커널 개입, 복사 2회). 동기화가 자동으로 보장되어 구현이 안전
파이프(Pipe) 단방향 통신. 익명 파이프는 부모-자식 간, 명명 파이프(FIFO)는 무관한 프로세스 간 간단, 단방향
소켓(Socket) 네트워크를 통한 통신. 다른 머신과도 가능 범용성 최고
시그널(Signal) 비동기 이벤트 통지 (SIGKILL, SIGCHLD 등) 데이터 전달이 아닌 "알림"
메시지 큐 커널이 관리하는 큐에 메시지 적재 비동기, 다대다 가능

시험 포인트: 공유 메모리는 빠르지만 동기화를 직접 해야 하고, 메시지 패싱은 느리지만 안전하다. 이 trade-off가 서술의 핵심.

1-4. CPU Scheduling 🔥 🧮 ✍️

선점형 vs 비선점형 🔥

선점형 (Preemptive) 비선점형 (Non-preemptive)
정의 OS가 실행 중인 프로세스로부터 CPU를 강제로 회수할 수 있음 프로세스가 스스로 CPU를 반납할 때까지 계속 실행
CPU 반납 시점 타이머 만료, 더 높은 우선순위 도착 종료 또는 I/O 대기 진입 시
장점 ① 응답 시간이 짧고 예측 가능
② 우선순위 높은 작업 즉시 처리
③ 한 프로세스의 CPU 독점 방지
→ 대화형/실시간 시스템에 적합		 ① Context Switching 오버헤드가 적음
② 구현이 단순
③ 처리량(Throughput) 높음
④ 모든 프로세스에 공정
단점 ① 잦은 Context Switching → 오버헤드
② 공유 데이터 접근 시 동기화(Race Condition) 문제 발생
③ 구현 복잡		 ① 짧은 작업이 긴 작업 뒤에서 오래 대기 → 호위 효과(Convoy Effect)
② 응답 시간 예측 어려움
③ 긴급한 작업 즉시 처리 불가
알고리즘 SRT, Round Robin, 선점형 우선순위, MLFQ FCFS, SJF, HRN, 비선점형 우선순위

스케줄링 알고리즘 정리

알고리즘 방식 선점 특징 / 문제점
FCFS (First Come First Served) 도착 순서대로 ❌ 가장 단순. Convoy Effect 발생
SJF (Shortest Job First) 실행시간 짧은 것부터 ❌ 평균 대기시간 최소(이론상 최적). 실행시간을 미리 알아야 함(비현실적), 기아(Starvation) 발생
SRT/SRTF (Shortest Remaining Time) 남은 실행시간 최소 ✅ SJF의 선점형. 새 프로세스 도착 때마다 비교
Priority 우선순위 순 둘 다 가능 기아 문제 → Aging(에이징) 으로 해결(대기 시간에 비례해 우선순위를 점점 높임)
Round Robin 타임 퀀텀만큼 돌아가며 ✅ 응답 시간 보장. 퀀텀이 너무 크면 FCFS화, 너무 작으면 Context Switching 오버헤드 폭증
HRN 우선순위 = (대기시간+실행시간)/실행시간 ❌ SJF의 기아 문제 보완
MLFQ (Multi-Level Feedback Queue) 여러 큐 사이 이동 ✅ CPU를 많이 쓰면 낮은 큐로 강등. 실행시간을 몰라도 SJF 근사 효과

🧮 계산 공식

대기 시간(Waiting Time)   = 시작 시간 - 도착 시간   (선점 시엔 CPU를 못 쓴 총 시간)
반환 시간(Turnaround Time) = 종료 시간 - 도착 시간
응답 시간(Response Time)   = 최초 CPU 할당 시간 - 도착 시간
반환 시간 = 대기 시간 + 실행 시간   ← 검산에 활용

🧮✍️ 완전 예제

프로세스 도착시간 실행시간
P1 0 3
P2 2 6
P3 4 4
P4 8 2

① FCFS 스케줄링 — 도착 순서 P1(0) → P2(2) → P3(4) → P4(8)

 0     3        9        13    15
 ├─P1──┼───P2───┼───P3───┼─P4──┤
  • P1: 0~3 / P2: 3~9 / P3: 9~13 / P4: 13~15
도착 종료 반환시간 대기시간
P1 0 3 3 0
P2 2 9 7 1
P3 4 13 9 5
P4 8 15 7 5

평균 반환시간 = (3+7+9+7)/4 = 6.5, 평균 대기시간 = (0+1+5+5)/4 = 2.75

② SRT 스케줄링 — 매 순간 남은 시간이 가장 짧은 것 선택

t=0  : P1만 존재(3) → P1 실행
t=2  : P1 남음 1, P2 도착 6 → P1 유지 (1 < 6)
t=3  : P1 종료. 후보 P2(6) → P2 실행
t=4  : P3 도착(4). P2 남음 5 vs P3 4 → P3가 짧음 → 선점! P3 실행
t=8  : P3 종료(4~8). P4 도착(2), P2 남음 5 → P4가 짧음 → P4 실행
t=10 : P4 종료. P2 남은 5 실행 → 15에 종료

 0     3    4        8     10        15
 ├─P1──┼─P2─┼───P3───┼─P4──┼───P2────┤
도착 종료 반환시간 대기시간
P1 0 3 3 0
P2 2 15 13 7
P3 4 8 4 0
P4 8 10 2 0

평균 반환시간 = (3+13+4+2)/4 = 5.5, 평균 대기시간 = (0+7+0+0)/4 = 1.75

결과 해석까지 쓰면 가점: SRT가 FCFS보다 평균 대기시간이 짧다(1.75 < 2.75). 대신 P2처럼 긴 작업이 계속 밀려 기아(Starvation) 위험이 있다.

⚠️ 간트차트 함정 1. 도착시간을 무시하고 그리는 실수 — t=0에 P3가 없다는 걸 놓치면 전부 틀린다. 2. SRT는 "남은 시간" 비교다. 원래 실행시간(SJF)이 아니다. 3. CPU가 놀고 있는 구간(idle) 이 생길 수 있다. 이때는 빈칸으로 표시한다. 4. 동점일 때 규칙(보통 FCFS 또는 문제 지시)을 답안에 명시한다.

1-5. 동기화 (Synchronization) 🔥

Race Condition (경쟁 상태)

둘 이상의 프로세스/스레드가 공유 데이터에 동시에 접근할 때, 실행 순서(타이밍)에 따라 결과가 달라지는 상황.

전형적 예시 — count++ 는 원자적(atomic)이지 않다:

count++ 의 실제 기계어:
  ① load  R1 ← count     (메모리 → 레지스터)
  ② add   R1 ← R1 + 1     (레지스터에서 증가)
  ③ store count ← R1      (레지스터 → 메모리)

count = 5 인 상태에서 T1, T2가 동시에 count++ 실행:
  T1: ① load R1=5
  ---- Context Switch ----
  T2: ① load R1=5  ② R1=6  ③ store count=6
  ---- Context Switch ----
  T1: ② R1=6  ③ store count=6   ← 결과 6. 정답은 7이어야 하는데 갱신 손실!

Critical Section (임계 구역)

공유 자원에 접근하는 코드 영역. 한 번에 하나의 프로세스만 진입해야 한다.

임계 구역 문제 해결의 3가지 조건 🔥 (서술 필수 암기)

조건 내용
상호 배제 (Mutual Exclusion) 한 프로세스가 임계 구역에 있으면 다른 프로세스는 진입할 수 없다
진행 (Progress) 임계 구역이 비어 있으면, 진입을 원하는 프로세스 중 하나는 반드시 진입할 수 있어야 한다 (교착 방지)
한정 대기 (Bounded Waiting) 진입을 요청한 프로세스는 유한한 시간 안에 반드시 진입할 수 있어야 한다 (기아 방지)

🔥 스핀락 vs 뮤텍스 시나리오 판단

판단 기준: "대기 시간 < Context Switching 비용" 이면 스핀락, 아니면 뮤텍스

시나리오 정답 이유
① 임계구간이 짧고 경쟁이 빈번 스핀락 대기 시간이 문맥 교환 비용보다 짧다. 잠깐 돌면서 기다리는 게 재우고 깨우는 것보다 싸다
② 임계구간이 길어 오래 락을 잡아야 함 뮤텍스 오래 스핀하면 CPU를 통째로 낭비한다. 재우고 다른 프로세스에 CPU를 넘기는 게 이득
③ 이미 다른 스핀락을 획득한 상태 스핀락 스핀락을 쥔 채 sleep하면, 그 락을 기다리는 다른 코어들이 전부 무한정 스핀하게 되어 시스템 전체가 마비된다. 락을 보유한 상태에서는 절대 잠들면 안 된다. (인터럽트 핸들러 문맥에서도 동일 — 잠들 수 없으므로 스핀락만 사용 가능)

③번이 이 문제의 핵심 함정이다. "스핀락 보유 중에는 sleep 금지"라는 원칙을 아는지를 묻는다.

⚠️ 스핀락의 전제: 스핀락은 멀티코어에서만 의미 있다. 싱글코어에서 스핀락을 쓰면, 락을 쥔 스레드가 CPU를 받지 못해 영원히 락을 못 푼다(타임 퀀텀 만료 전까지 낭비).

모니터(Monitor) △

세마포어는 P/V 연산 순서를 실수하기 쉽다. → 공유 자원 + 접근 함수 + 동기화를 하나의 객체로 캡슐화한 고수준 동기화 도구. Java의 synchronized 키워드가 대표적 구현.

1-6. Deadlock (교착 상태) 🔥 🧮

정의

둘 이상의 프로세스가 서로가 점유한 자원을 무한정 기다리며, 어느 쪽도 진행하지 못하는 상태.

🔥 발생 4가지 필요조건 (전부 성립해야 발생)

조건 설명
상호 배제 (Mutual Exclusion) 한 자원은 한 번에 한 프로세스만 사용 가능
점유와 대기 (Hold and Wait) 자원을 점유한 채로 다른 자원을 추가로 기다림
비선점 (No Preemption) 다른 프로세스가 점유한 자원을 강제로 빼앗을 수 없음
환형 대기 (Circular Wait) 프로세스들이 원형으로 서로의 자원을 기다림 (P1→P2→P3→P1)

암기법: "상 점 비 환". 네 개 중 하나라도 깨면 교착 상태는 발생하지 않는다 → 이것이 예방(Prevention)의 원리.

해결 방법 4가지 🔥

① 예방 (Prevention) — 4가지 조건 중 하나를 사전에 무너뜨림

깨는 조건 방법 부작용
상호 배제 부정 자원을 공유 가능하게 만듦 (읽기 전용 파일 등) 대부분의 자원은 본질적으로 공유 불가(프린터 등) → 현실성 낮음
점유와 대기 부정 프로세스 시작 전에 필요한 모든 자원을 한꺼번에 할당하거나, 자원 요청 시 가진 자원을 모두 반납 자원 이용률 저하, 기아 발생 가능
비선점 부정 추가 자원 요청이 거절되면 가진 자원을 모두 반납하고 재요청 상태 저장/복원 비용 큼. CPU·메모리처럼 상태 저장이 쉬운 자원에만 적용 가능
환형 대기 부정 모든 자원에 번호를 부여하고 오름차순으로만 요청 자원 사용 순서에 제약 → 비효율

답안 형태: "교착상태를 사전에 예방하는 방법을 설명하시오" → 4가지 필요조건을 먼저 제시하고, 각 조건을 무너뜨리는 방법을 하나씩 서술하면 만점 구조가 된다.

② 회피 (Avoidance) — 자원 할당 시점에 안전한지 검사

  • 안전 상태(Safe State): 모든 프로세스가 자원을 할당받아 완료될 수 있는 순서(안전 순서열) 가 최소 하나 존재하는 상태
  • 안전 상태 → 교착 상태 아님. 불안전 상태 → 교착 상태 가능성 있음 (반드시 발생하는 건 아님!)
  • 대표 알고리즘: 은행원 알고리즘(Banker's Algorithm), 자원 할당 그래프 알고리즘

③ 탐지 (Detection) & ④ 회복 (Recovery)

  • 교착 상태 발생을 허용하고, 주기적으로 자원 할당 그래프의 사이클을 탐지
  • 회복: (a) 프로세스 강제 종료 (전부 / 하나씩) (b) 자원 선점하여 다른 프로세스에 할당 → 희생자 선택(Victim Selection) 기준 필요, 기아 방지 고려
  • ④ 무시 (Ostrich Algorithm): 발생 빈도가 매우 낮으면 그냥 무시. 대부분의 범용 OS(Linux, Windows)가 채택 — 예방/회피 비용이 더 크기 때문

🧮 Banker's Algorithm 완전 예제

문제: 시스템 총 자원 12개. 아래 표를 보고 가용 자원을 어떤 순서로 할당할 수 있는지 쓰시오.

프로세스 할당 중인 자원량(Allocation) 추가로 필요한 자원량(Need)
P0 5 5
P1 2 2
P2 2 7

Step 0. 가용 자원(Available) 계산

Available = 전체 자원 - 할당된 자원 합
          = 12 - (5 + 2 + 2)
          = 12 - 9 = 3

Step 1. Need ≤ Available 인 프로세스를 찾는다

P0: Need 5 > 3  ✗
P1: Need 2 ≤ 3  ✅ ← 선택
P2: Need 7 > 3  ✗

→ P1에게 2를 할당해 실행. P1 종료 시 보유 자원 전부 반납

Available = 3 - 2 + (2 + 2) = 5
            (할당)    (P1이 반납: 원래 2 + 받은 2)

Step 2. Available = 5

P0: Need 5 ≤ 5  ✅ ← 선택
P2: Need 7 > 5  ✗

→ P0 실행 후 반납: Available = 5 - 5 + (5 + 5) = 10

Step 3. Available = 10

P2: Need 7 ≤ 10 ✅ → 실행 후 종료

✅ 답: 안전 순서열 = P1 → P0 → P2 (이 시스템은 안전 상태이다)

⚠️ 은행원 알고리즘 함정 1. Available을 먼저 구하지 않고 시작하는 실수 — Available = Total - ΣAllocation 2. Need = Max - Allocation 이다. 문제가 Max를 주면 빼야 하고, Need를 직접 주면 그대로 쓴다. (이 문제는 Need를 직접 줬다) 3. 프로세스가 종료되면 원래 할당분 + 새로 받은 분을 모두 반납한다. 4. 안전 순서열은 여러 개일 수 있다. 하나만 찾으면 안전 상태로 판정한다.

은행원 알고리즘의 한계 (서술 시 가점) - 프로세스가 최대 요구량을 미리 선언해야 한다 (현실적으로 어려움) - 프로세스 수와 자원 수가 고정되어야 한다 - 자원 이용률이 낮아진다 (보수적으로 판단) - 매 요청마다 O(n²m) 검사 → 오버헤드

교착 상태 — 기억 장치와 OS·DB 대응표 🔥

비선점이 안 외워질 때 — 좁은 골목의 차 두 대 한 칸엔 한 대(상호 배제), 자기 자리를 차지한 채 앞을 기다림(점유와 대기), 견인차가 없음 = 상대 차를 강제로 치울 수 없음(비선점), 서로가 서로를 막음(순환 대기). 견인차를 부르는 것 = 선점 허용.

깨는 조건 방법 (OS) 방법 (DB 트랜잭션)
상호 배제 공유 가능하게(읽기 전용) 읽기는 S-lock 공유, 쓰기 X-lock은 불가피
점유와 대기 필요한 자원을 한꺼번에 요청 보수적 2PL
비선점 다른 프로세스 자원을 빼앗을 수 있게 Wound-Wait(오래된 T가 젊은 T를 ROLLBACK)
순환 대기 자원에 번호를 매겨 오름차순으로만 요청 데이터 항목 순서대로 lock, Wait-Die(젊은 T가 포기)
  • 예방 vs 회피: 예방은 규칙을 바꿔 교착이 구조적으로 불가능하게, 회피는 규칙은 그대로 두고 요청마다 안전 상태를 계산해 판단(은행원).

테이블 항목 프레임 번호 base(시작주소) + limit(길이)
단편화 내부 단편화 발생 외부 단편화 발생
보호/공유 페이지 단위 (논리 단위와 안 맞아 부자연스러움) 논리 단위라 보호·공유에 유리 (예: Code 세그먼트만 읽기 전용 공유)
주소 유효성 검사 불필요 (크기가 같으므로) 필요 (오프셋 d < limit 인지 검사)

현대 OS는 둘을 결합한다(Paged Segmentation). 세그먼트를 논리 단위로 나누고, 각 세그먼트를 다시 페이지로 나눠 외부 단편화를 없앤다. x86이 대표적.

🧮 주소 변환 (Address Translation)

논리 주소(Logical Address) = [ 페이지 번호 p | 오프셋(변위) d ]

논리 주소 공간 = 2^m,  페이지 크기 = 2^n  일 때
   → 오프셋 d 는 n 비트,  페이지 번호 p 는 (m - n) 비트
   → 페이지 테이블 항목 수 = 2^(m-n)

물리 주소 = 프레임 번호(f) × 페이지 크기 + 오프셋(d)

예제: 논리 주소 32비트, 페이지 크기 4KB

4KB = 2^12  → 오프셋 12비트
페이지 번호 = 32 - 12 = 20비트
페이지 테이블 항목 수 = 2^20 = 약 100만 개
항목 하나가 4Byte라면 테이블 크기 = 4MB (프로세스당!)
→ 이래서 다단계 페이지 테이블(Multi-level Page Table)이 필요하다

⚠️ 함정: 페이지 크기가 4KB면 2^12이지 2^4가 아니다. KB=2^10, MB=2^20, GB=2^30을 반드시 정확히 변환할 것.

TLB (Translation Lookaside Buffer) 🔥 🧮

등장 배경: 페이지 테이블은 메모리에 있다. 그래서 주소 변환에 메모리 접근 1회 + 실제 데이터 접근 1회 = 총 2회 필요 → 속도 절반. → 최근 사용한 주소 변환 결과를 캐시하자 = TLB (주소 변환 전용 캐시)

🧮 EAT (Effective Access Time, 유효 접근 시간) 공식

TLB Hit  : TLB 접근 시간 + 메모리 접근 시간
TLB Miss : TLB 접근 시간 + 메모리 접근(페이지 테이블) + 메모리 접근(실제 데이터)

EAT = h × (t + m) + (1-h) × (t + 2m)
    (h = TLB 히트율, t = TLB 접근 시간, m = 메모리 접근 시간)

  ※ TLB 접근 시간을 무시하는 문제라면:
    EAT = h × m + (1-h) × 2m = (2 - h) × m

예제: TLB 접근 20ns, 메모리 접근 100ns, 히트율 80%

EAT = 0.8 × (20 + 100) + 0.2 × (20 + 100 + 100)
    = 0.8 × 120 + 0.2 × 220
    = 96 + 44 = 140ns

⚠️ 함정: 문제가 "TLB 접근 시간을 무시한다"고 했는지 확인. 그리고 TLB Miss 시 메모리를 2번 접근한다는 걸 놓치지 말 것. 답안에 가정을 명시하면 채점자가 판단해 준다.

가상 메모리 (Virtual Memory) & Demand Paging 🔥

핵심 아이디어: 프로그램 전체가 메모리에 있을 필요는 없다. 지금 실행 중인 부분만 있으면 된다(지역성의 원리). → 물리 메모리보다 큰 프로그램도 실행 가능, 다중 프로그래밍 정도 상승.

요구 페이징(Demand Paging): 페이지를 미리 올리지 않고, 실제 참조될 때(요구가 있을 때) 메모리로 가져온다.

Valid/Invalid Bit: 페이지 테이블의 각 항목에 있는 비트. invalid면 그 페이지는 메모리에 없다(디스크에 있다).

Page Fault 처리 과정 🔥 ✍️

1. 프로세스가 페이지 참조
2. 페이지 테이블 확인 → invalid bit 발견
3. Trap 발생 → 커널 모드 전환 (Page Fault Trap)
4. OS가 정말 잘못된 접근인지 확인 (아니면 프로세스 종료)
5. 빈 프레임 찾기
   └─ 빈 프레임이 없으면 → Page Replacement 알고리즘으로 희생 페이지 선정
      └─ 희생 페이지가 수정됐다면(Dirty bit=1) 디스크에 먼저 write-back
6. 디스크에서 해당 페이지를 프레임으로 읽어옴 (I/O — 매우 느림)
7. 페이지 테이블 갱신 (valid bit = 1, 프레임 번호 기록)
8. 중단됐던 명령어를 재실행

Page Fault는 인터럽트(Trap)이지 에러가 아니다. 이걸 "오류"라고 서술하면 감점. 정상적인 요구 페이징 동작의 일부다.

🔥 Page Replacement Algorithm

참조 스트링(Reference String) 이 주어지고 프레임 수가 정해지면, 각 알고리즘의 Page Fault 횟수를 세는 문제로 나온다.

알고리즘 교체 대상 특징
FIFO 가장 먼저 들어온 페이지 구현 단순. Belady's Anomaly 발생 (프레임을 늘렸는데 Page Fault가 증가하는 역설)
OPT (OPTimal) 앞으로 가장 오랫동안 사용되지 않을 페이지 Page Fault 최소(이론상 최적). 미래를 알아야 하므로 실제 구현 불가 → 다른 알고리즘의 성능 평가 기준으로만 사용
LRU (Least Recently Used) 가장 오래전에 사용된 페이지 (과거 기준) OPT의 현실적 근사. 시간적 지역성 활용. 실제로 가장 널리 쓰임. 구현 비용 큼(참조 시각 기록 또는 연결 리스트)
LFU (Least Frequently Used) 참조 횟수가 가장 적은 페이지 초기에 많이 참조된 후 안 쓰이는 페이지가 계속 남는 문제. 최근 막 올라온 페이지가 바로 쫓겨남(횟수 0). 동점 시 LRU 등 추가 기준 필요
MFU 참조 횟수가 가장 많은 페이지 "많이 썼으니 이제 안 쓸 것"이라는 가정. 잘 안 쓰임
Clock (2nd Chance) 참조 비트 0인 페이지 LRU 근사. 참조 비트가 1이면 0으로 바꾸고 한 번 더 기회. 실제 OS가 채택

🧮 예제 — 참조 스트링 7 0 1 2 0 3 0 4 2 3, 프레임 3개

【FIFO】
참조:  7   0   1   2   0   3   0   4   2   3
      ─────────────────────────────────────
F1:   7   7   7   2   2   2   2   4   4   4
F2:       0   0   0   0   3   3   3   2   2
F3:           1   1   1   1   0   0   0   3
Fault: F   F   F   F   -   F   F   F   F   F   → 9회

【OPT】 (미래를 봄)
참조:  7   0   1   2   0   3   0   4   2   3
F1:   7   7   7   2   2   2   2   2   2   2
F2:       0   0   0   0   0   0   4   4   3
F3:           1   1   1   3   3   3   3   3
Fault: F   F   F   F   -   F   -   F   -   F   → 7회
  t=4(2 적재): 7,0,1 중 7이 다시 안 나옴 → 7 축출
  t=8(4 적재): 2,0,3 중 0이 다시 안 나옴 → 0 축출

【LRU】 (과거를 봄)
참조:  7   0   1   2   0   3   0   4   2   3
F1:   7   7   7   2   2   2   2   4   4   3
F2:       0   0   0   0   0   0   0   0   0
F3:           1   1   1   3   3   3   2   2
Fault: F   F   F   F   -   F   -   F   F   F   → 8회

→ OPT(7) < LRU(8) < FIFO(9) — 항상 이 경향이 나온다. 검산에 활용할 것.

⚠️ 페이지 교체 함정 1. 적재 시점 vs 참조 시점 혼동 — LRU는 "마지막으로 참조된 시점"이 기준이다. Hit도 참조로 카운트한다. 2. 처음 프레임을 채우는 것도 Page Fault로 센다. 3. LFU는 동점이 자주 발생한다. 동점 처리 규칙(보통 LRU 병용)을 답안에 명시. 4. Belady's Anomaly는 FIFO에서만 발생한다. LRU·OPT는 스택 알고리즘(Stack Algorithm) 이라 발생하지 않는다.

🔥 Thrashing (스래싱)

CPU
이용률
  │        ╭──────╮
  │      ╱          ╲
  │    ╱              ╲      ← "스래싱(Thrashing)"
  │  ╱                  ╲
  │╱                      ╲___
  └───────────────────────────── 다중 프로그래밍의 정도

정의: 프로세스가 실제 실행보다 페이지 교체(Swap In/Out)에 더 많은 시간을 소비하여, 다중 프로그래밍 정도를 높였는데도 CPU 이용률이 급격히 떨어지는 현상.

발생 이유 (악순환 구조) — 이 인과 사슬을 그대로 서술하면 만점

1. 다중 프로그래밍 정도 ↑ → 프로세스당 할당 프레임 수 ↓
2. 프로세스가 Working Set(당장 필요한 페이지 집합)조차 담지 못함
3. Page Fault 폭증
4. 페이지를 가져오려 디스크 I/O 대기 → 프로세스가 Blocked
5. CPU가 놀게 됨 → CPU 이용률 하락
6. OS가 "CPU가 놀고 있네? 프로세스를 더 올리자"고 오판
7. → 1번으로 돌아가 악순환 심화 → CPU 이용률 급락

방법 설명

페이지 종류별 축출 처리 🔥

문제: 페이지는 (a) 보조저장장치에서 읽어온 파일 데이터와 (b) 프로세스의 스택·힙 등 실행 데이터로 나뉜다. 메모리 부족으로 내보내야 할 때 각각 어떻게 처리하는가?

페이지 종류 처리 방식 이유
파일 데이터 페이지 (File-backed Page: 실행 파일 코드, mmap된 파일) 수정 안 됐으면(Dirty bit=0) 그냥 버린다. 수정됐으면(Dirty bit=1) 원본 파일에 write-back 후 버린다 원본이 이미 디스크의 파일에 존재하므로, 다시 필요하면 그 파일에서 읽어오면 된다. 스왑 영역에 복사할 이유가 없다
실행 데이터 페이지 (Anonymous Page: 스택, 힙, 초기화된 전역변수 등) 반드시 스왑 영역(Swap Space)에 기록한 뒤 버린다 디스크에 대응하는 원본 파일이 없다. 그냥 버리면 데이터가 영구 소실된다

핵심 개념: Dirty Bit(수정 비트). 페이지가 메모리에 올라온 뒤 수정됐는지를 표시. Dirty=0이면 디스크 write 없이 버릴 수 있어 축출 비용이 0에 가깝다. → 교체 알고리즘은 가능하면 Dirty=0 페이지를 우선 희생시킨다.

MMU (Memory Management Unit) 🔥

정의: CPU가 내보내는 논리(가상) 주소를 물리 주소로 변환하는 하드웨어 장치. 주소를 변환할 때마다 운영체제를 부르면 너무 느리기 때문에, 변환을 하드웨어가 매 메모리 접근마다 직접 처리한다.

MMU의 역할 내용
① 주소 변환 페이지 번호 → 페이지 테이블 조회 → 프레임 번호로 교체 (TLB를 내장해 캐싱)
② 메모리 보호 페이지 테이블 항목의 권한 비트(읽기/쓰기/실행, 사용자/커널)를 검사해 위반 시 예외 발생
③ 페이지 부재 감지 valid bit = 0이면 Page Fault 인터럽트를 발생시켜 OS가 디스크에서 페이지를 적재하도록 함

가상 메모리를 사용했을 때의 이점 (서술 5가지)

  1. 물리 메모리보다 큰 프로그램 실행 — 필요한 페이지만 적재(Demand Paging)
  2. 프로세스 간 격리·보호 — 각 프로세스가 독립된 가상 주소 공간을 가져 남의 메모리에 접근 불가
  3. 메모리 공유 — 같은 물리 프레임을 여러 프로세스의 페이지 테이블에 매핑(공유 라이브러리, fork()의 Copy-on-Write)
  4. 다중 프로그래밍 정도 향상 — 프로세스당 적재 페이지가 적어 더 많은 프로세스를 동시에 올림 → CPU 이용률 상승
  5. 외부 단편화 해소·프로그래밍 단순화 — 연속된 물리 공간이 필요 없고, 프로그래머는 0번지부터 시작하는 주소만 신경 쓰면 됨

페이지화된 세그먼테이션 (Paged Segmentation) 🔥 🧮

등장 배경: 세그먼테이션은 논리 단위(코드·데이터·스택) 보호·공유가 좋지만 외부 단편화가 생기고, 페이징은 외부 단편화가 없지만 논리 단위와 맞지 않는다. → 세그먼트로 나눈 뒤, 각 세그먼트를 다시 페이지로 나눈다.

논리 주소 = [ 세그먼트 번호 s | 페이지 번호 p | 페이지 변위 d ]
                                └──── 세그먼트 변위 ────┘

① 세그먼트 테이블[s] → 그 세그먼트의 페이지 테이블 위치
② 해당 페이지 테이블[p] → 프레임 번호 f
③ 물리 위치 = 프레임 f 의 변위 d

예) (설명용 임의 값) s = 011₂ = 3, p = 01₂ = 1, d = 0101₂ = 5
    → 세그먼트 3의 페이지 테이블에서 PTE 1을 찾아 프레임 번호 f
    → 답: "프레임 f, 변위 5" (10진수로)
장점 단점
세그먼트 단위 보호·공유 + 외부 단편화 제거 테이블을 2단계로 거쳐 메모리 접근 증가(TLB로 완화)
세그먼트 크기가 커도 필요한 페이지만 적재 페이지 단위라 마지막 페이지의 내부 단편화는 남음

풀이 습관: 2진 필드를 반드시 10진수로 바꿔 쓴 뒤 테이블을 찾는다. 답이 "10진수로" 요구되면 프레임 번호와 변위를 둘 다 10진수로 쓴다.

외부 단편화는 왜 생기나 — 예시

단계 메모리 100KB
A 30, B 20, C 30, D 20 적재 [A 30][B 20][C 30][D 20]
B, D 종료 [A 30][빈 20][C 30][빈 20]
E(35KB) 요청 빈 공간 총 40KB인데 연속 35KB가 없어 적재 불가
  • 해결: 압축(Compaction)으로 빈 공간을 한데 모으기, 또는 고정 크기로 나누는 페이징.
  • 🔥 LRU 정의는 "가장 오랫동안 참조되지 않은(마지막 참조 시점이 가장 오래된) 페이지"라고 쓴다. "가장 마지막으로 참조된"은 MRU(방금 쓴 페이지)로 읽힐 수 있다.

1-8. 코드 해석형 — fork / exec / wait 🔥

#include <sys/types.h>
#include <stdio.h>
#include <unistd.h>
int main() {
    pid_t pid;
    pid = fork();
    if (pid < 0) {
        fprintf(stderr, "Fork failed");
        return 1;
    } else if (pid == 0) {          // 자식 프로세스
        execlp("/bin/ls", "ls", NULL);
        printf("Hello World");      // ← 이 줄이 문제
    } else {                         // 부모 프로세스
        wait(NULL);
        printf("Child Complete");
    }
    return 0;
}

각 시스템 콜의 의미

함수 동작 반환값
fork() 현재 프로세스를 복제해 자식 프로세스 생성. 자식은 부모의 주소 공간 사본을 가짐(실제로는 COW, Copy-On-Write 로 지연 복사) 부모에겐 자식의 PID(>0), 자식에겐 0, 실패 시 음수
exec() 계열 현재 프로세스의 주소 공간을 새 프로그램으로 완전히 덮어씀. 새 프로세스를 만드는 게 아니라 껍데기(PID)는 그대로 두고 내용물만 교체 성공하면 반환하지 않는다 (돌아올 코드가 사라졌으므로)
wait() 자식 프로세스가 종료될 때까지 부모를 Blocked 상태로 대기시키고, 종료 시 자식의 종료 상태를 수거 종료된 자식의 PID

✅ 실행 결과와 이유

결과: ls 명령의 실행 결과(디렉터리 목록)가 출력된 뒤, Child Complete 가 출력된다. "Hello World" 는 출력되지 않는다.

이유: execlp()가 성공하면 자식 프로세스의 주소 공간(Code/Data/Heap/Stack)이 /bin/ls 프로그램의 이미지로 완전히 대체된다. printf("Hello World") 라는 코드 자체가 메모리에서 사라지므로 실행될 수 없다. execlp()는 성공 시 호출한 지점으로 반환하지 않는다. printf("Hello World") 가 실행되는 유일한 경우는 execlp()가 실패했을 때다(경로 오류 등). 따라서 실무에서는 exec 계열 호출 바로 다음 줄에 에러 처리 코드를 둔다.

wait(NULL) 의 역할과 누락 시 문제점 🔥

역할 1. 부모 프로세스를 자식이 종료될 때까지 Blocked 상태로 대기시킨다 → 출력 순서 보장(ls 결과 → Child Complete) 2. 종료된 자식의 종료 상태(exit status)를 수거하여, 커널이 자식의 PCB를 완전히 정리하게 한다

누락 시 문제점

문제 설명
① 좀비 프로세스(Zombie Process) 자식은 종료됐지만 부모가 종료 상태를 수거하지 않아, PCB(프로세스 테이블 엔트리)가 계속 남아있는 상태. 좀비가 쌓이면 PID 자원이 고갈되어 새 프로세스를 만들 수 없게 된다
② 실행 순서 비결정성 부모와 자식이 동시에 실행되어 출력 순서가 매 실행마다 달라진다. Child Complete 가 ls 결과보다 먼저 나올 수 있다
③ 고아 프로세스(Orphan Process) 부모가 자식보다 먼저 종료되면 자식은 고아가 된다. 이 경우는 init(PID 1)/systemd 프로세스가 입양하여 대신 정리해 주므로 좀비만큼 위험하진 않다

좀비 vs 고아 구별 — 시험 단골: - 좀비: 자식이 먼저 죽고 부모가 안 거둠 → 위험(자원 누수) - 고아: 부모가 먼저 죽음 → init이 입양해서 처리 → 상대적으로 안전

스레드 풀 (Thread Pool)

요청마다 스레드를 만들면 생성/소멸 비용과 스레드 수 폭증에 따른 문맥 교환·메모리 부족이 생긴다. → 미리 만들어 둔 스레드가 작업 큐에서 일을 꺼내 처리한다.

설정너무 작으면너무 크면
스레드 수큐 대기 증가, 응답 지연문맥 교환·메모리 낭비
큐 크기요청 거절 증가지연이 숨겨지고 메모리 고갈
  • 적정 스레드 수 근사: CPU 위주 작업 = 코어 수 (+1), I/O 위주 작업 = 코어 수 × (1 + 대기 시간 / 연산 시간)
  • 큐가 가득 찼을 때의 정책(거절, 호출자 실행, 가장 오래된 작업 버림)을 반드시 정한다.

Thread-safe · 재진입 가능

  • Thread-safe: 여러 스레드가 동시에 호출해도 결과가 올바른 것. 방법 — 상호 배제(락), 불변 객체, 스레드 지역 저장소(TLS), 원자적 연산.
  • 재진입 가능(Reentrant): 실행 도중 같은 함수가 다시 호출되어도 안전한 것. 전역/정적 상태를 쓰지 않고 인자와 지역 변수만 쓴다. 재진입 가능하면 thread-safe 하지만 역은 성립하지 않는다(락을 쓰는 함수는 thread-safe 하지만 시그널 핸들러에서 재진입하면 교착).

CAS와 락-프리

// Compare-And-Swap: 하드웨어가 원자적으로 보장
bool CAS(int *addr, int expected, int new_val) {
    if (*addr == expected) { *addr = new_val; return true; }
    return false;
}
// 락 없이 증가
do { old = counter; } while (!CAS(&counter, old, old + 1));

  • 파일 디스크립터(fd): 프로세스별 정수 핸들. 0·1·2 는 표준 입력·출력·에러.

inode

파일 하나당 하나씩 있는 메타데이터 구조체. 파일 종류, 권한, 소유자, 크기, 시각, 링크 수, 데이터 블록 위치를 담는다. 파일 이름은 inode 에 없다 — 이름은 디렉터리 엔트리(이름 → inode 번호)에 있다.

inode
├─ 직접 포인터 12개      → 데이터 블록
├─ 단일 간접 포인터 1개   → [포인터 블록] → 데이터 블록
├─ 이중 간접 포인터 1개   → [포인터 블록] → [포인터 블록] → 데이터 블록
└─ 삼중 간접 포인터 1개

예제. 블록 크기 4KB, 블록 주소 4바이트, 직접 포인터 12개 + 단일·이중·삼중 간접 포인터가 각 1개일 때 최대 파일 크기는?

풀이
  • 포인터 블록 하나에 들어가는 주소 수 = 4KB / 4B = 1024개
  • 직접: 12 × 4KB = 48KB
  • 단일 간접: 1024 × 4KB = 4MB
  • 이중 간접: 1024² × 4KB = 4GB
  • 삼중 간접: 1024³ × 4KB = 4TB
  • 합계 ≈ 4TB (삼중 간접 항이 지배)

1-14. 가상 메모리 실무 — COW · mmap · 스왑 ⭐

Copy-on-Write (COW)

fork() 가 부모의 메모리를 전부 복사하면 느리고, 곧바로 exec() 하면 복사가 헛수고다.

  1. fork() 시 페이지를 복사하지 않고 부모·자식이 같은 물리 프레임을 공유하며, 둘 다 읽기 전용으로 표시한다.
  2. 어느 한쪽이 쓰려 하면 보호 폴트가 발생한다.
  3. 커널이 그 페이지 하나만 복사해 쓴 쪽에 새 프레임을 준다.
  • 활용 예: Redis 의 RDB 스냅샷은 fork() 후 자식이 메모리를 디스크에 쓴다. 그동안 부모가 쓰기를 많이 하면 복사되는 페이지가 늘어 메모리 사용량이 최대 2배까지 커질 수 있다.

메모리 맵 파일 (mmap)

파일을 프로세스 주소 공간에 직접 매핑한다. 접근하면 페이지 폴트로 해당 부분만 페이지 캐시에 올라온다.

구분read() / write()mmap()
복사커널 버퍼 → 사용자 버퍼 복사페이지 캐시를 직접 봄 (복사 없음)
시스템 콜호출마다매핑 때 한 번
적합순차 처리, 작은 I/O큰 파일의 임의 접근, 프로세스 간 공유
  • 제로 카피(zero-copy): sendfile() 은 파일 → 소켓 전송을 사용자 공간을 거치지 않고 커널 안에서 처리한다. 복사와 모드 전환이 줄어 Kafka, Nginx 같은 서버가 정적 데이터 전송에 쓴다.
  • 공유 메모리: 여러 프로세스가 같은 프레임을 매핑하면 커널을 거치지 않는 가장 빠른 IPC 가 된다. 대신 동기화는 직접 해야 한다.

좀비 프로세스 vs 고아 프로세스

구분좀비 (Zombie)고아 (Orphan)
상태자식이 종료했는데 부모가 wait() 로 종료 상태를 회수하지 않음부모가 먼저 종료해 자식만 남음
남는 것PCB(프로세스 테이블 항목)만 남음, 메모리는 해제됨정상 실행 중인 프로세스
문제쌓이면 PID 고갈대체로 무해 (의도치 않으면 자원 낭비)
처리부모가 wait() 호출, 또는 부모를 종료init(PID 1) 이 입양해 종료 시 회수
  • 좀비는 이미 죽었으므로 kill 로 없앨 수 없다. 부모를 종료시키면 init 이 입양해 회수한다.
  • 컨테이너에서 PID 1 로 돌린 애플리케이션이 자식 회수를 하지 않으면 좀비가 쌓인다. 그래서 tini 같은 최소 init 을 PID 1 로 둔다.

데몬 (Daemon)

터미널과 분리되어 백그라운드에서 계속 도는 서비스 프로세스(sshd, nginx 등). 전통적인 생성 절차는 fork() → 부모 종료 → setsid() 로 새 세션 생성 → 작업 디렉터리 변경 → 표준 입출력 닫기. 현대 리눅스는 systemd 가 서비스 수명·재시작·로그를 관리하므로 프로그램이 직접 데몬화할 필요가 줄었다.

부팅 과정

  1. 전원 → 펌웨어(BIOS/UEFI) 가 하드웨어 점검(POST)
  2. 부팅 장치에서 부트로더(GRUB) 적재
  3. 부트로더가 커널과 초기 램디스크(initramfs)를 메모리에 올림
  4. 커널이 장치·메모리·스케줄러 초기화 후 루트 파일 시스템 마운트
  5. PID 1 (systemd) 실행 → 서비스 기동 → 로그인 프롬프트
