12-1. 리눅스 실무 🔥 🧮

파일 권한

-rwxr-xr--  1  alice  dev  4096  app.sh
│└┬┘└┬┘└┬┘
│ │  │  └─ 기타 사용자 (other):  r--  = 4
│ │  └──── 그룹 (group):        r-x  = 5
│ └─────── 소유자 (user):       rwx  = 7
└───────── 파일 종류 (- 일반, d 디렉터리, l 심볼릭 링크)
권한값파일에서디렉터리에서
r (읽기)4내용 읽기목록 보기 (ls)
w (쓰기)2내용 수정안의 파일 생성·삭제·이름 변경
x (실행)1실행진입 (cd), 안의 파일에 접근

예제. (1) chmod 640 secret.txt 의 의미는? (2) umask 가 027 일 때 새로 만든 파일과 디렉터리의 권한은?

풀이
  1. 6 = rw-, 4 = r--, 0 = --- → 소유자는 읽기·쓰기, 그룹은 읽기, 기타는 접근 불가.
  2. 기본 권한에서 umask 비트를 제거한다. 파일의 기본은 666, 디렉터리의 기본은 777.
    • 파일: 666 에서 027 제거 → 640 (rw-r-----)
    • 디렉터리: 777 에서 027 제거 → 750 (rwxr-x---)
    • 단순 뺄셈이 아니라 비트 연산(기본 AND NOT umask)이다. 예: umask 033 → 파일은 666 − 033 = 633 이 아니라 644.
특수 권한효과예
SetUID (4000)실행하는 동안 파일 소유자 권한으로 동작passwd
SetGID (2000)그룹 권한으로 동작. 디렉터리에서는 새 파일이 그 그룹을 상속공유 디렉터리
Sticky bit (1000)디렉터리 안의 파일을 소유자만 삭제 가능/tmp
  • chown user:group file (소유자 변경), chmod u+x file (기호 방식), sudo (관리자 권한으로 실행).

SSH 키 인증

  1. 클라이언트에서 키 쌍 생성(ssh-keygen). 개인키는 내 컴퓨터에, 공개키는 서버의 ~/.ssh/authorized_keys 에 둔다.
  2. 접속 시 서버가 임의 값을 보내고, 클라이언트가 개인키로 서명해 돌려준다.
  3. 서버가 공개키로 검증한다. 패스워드가 네트워크로 전달되지 않는다.
  • 운영 서버는 패스워드 로그인과 root 직접 로그인을 막고, 배스천(점프) 호스트를 거쳐 접속하게 한다.

12-2. Git 실무 🔥

세 영역과 기본 흐름

작업 디렉터리 ──git add──▶ 스테이징 영역 ──git commit──▶ 로컬 저장소 ──git push──▶ 원격 저장소
      ◀────────────────── git restore / checkout ─────────────  ◀──── git fetch / pull ────
  • Git 은 변경분(diff)이 아니라 스냅샷을 저장하고, 커밋은 부모 커밋을 가리킨다. 브랜치는 커밋을 가리키는 포인터일 뿐이라 만들고 지우는 비용이 거의 없다.
  • git pull = git fetch + git merge. 형상 관리의 개념과 Git/SVN 비교는 → 형상관리

merge vs rebase

구분mergerebase
동작두 브랜치를 잇는 병합 커밋 생성내 커밋들을 대상 브랜치 끝으로 옮겨 다시 만듦
이력실제 일어난 그대로 (갈라졌다 합쳐짐)일직선
커밋 해시유지바뀜
충돌 해결한 번커밋마다
주의이력이 복잡해질 수 있음이미 공유한(push 한) 커밋은 rebase 하지 않는다
  • fast-forward 병합: 대상 브랜치에 새 커밋이 없으면 포인터만 앞으로 옮긴다(병합 커밋 없음).
  • squash 병합: 브랜치의 커밋들을 하나로 합쳐 반영. 기능 단위로 이력을 깔끔하게.

되돌리기

명령효과이력쓰는 때
git restore <file>작업 디렉터리의 변경을 버림—아직 커밋하지 않은 수정 취소

트렁크 기반main 에 하루에도 여러 번 작은 단위로 병합병합 충돌 최소, 피처 플래그 필요CI/CD 가 성숙한 팀

충돌과 협업

  • 충돌은 같은 부분을 서로 다르게 고쳤을 때 생긴다. 표시(<<<<<<<, =======, >>>>>>>) 사이를 정리하고 add → commit(또는 rebase --continue).
  • 줄이는 법: 브랜치 수명을 짧게, 자주 최신을 받아 오기, 작은 PR.
  • 좋은 PR: 한 가지 목적, 작게, 무엇을 왜 바꿨는지와 검증 방법을 설명.
  • 커밋 메시지: 제목에 "무엇을", 본문에 "왜". 관례 예: feat:, fix:, refactor:, docs:, test:.
  • .gitignore 에 빌드 산출물·비밀 정보를 넣는다. 한번 커밋된 비밀은 이력에 남으므로 폐기하고 재발급한다.

12-3. 컨테이너 — Docker 🔥

컨테이너가 푸는 문제

"내 컴퓨터에서는 되는데"를 없앤다. 애플리케이션과 실행에 필요한 모든 것(런타임, 라이브러리, 설정)을 이미지 하나로 묶어 어디서나 같게 실행한다. 가상 머신과의 비교는 → 하이퍼바이저 vs 컨테이너

리눅스 기능역할
네임스페이스보이는 것을 격리 — PID, 네트워크, 마운트, 사용자, 호스트명
cgroups쓸 수 있는 양을 제한 — CPU, 메모리, I/O
유니온 파일 시스템읽기 전용 레이어를 겹쳐 하나의 파일 시스템으로

컨테이너는 가상 머신이 아니라 격리된 프로세스다. 호스트의 커널을 공유한다.

이미지와 컨테이너

개념설명비유

컨테이너이미지를 실행한 인스턴스. 맨 위에 쓰기 가능 레이어 하나가 붙는다객체

# 멀티 스테이지 빌드: 빌드 도구는 최종 이미지에 넣지 않는다

WORKDIR /app
COPY pom.xml mvnw ./
COPY .mvn .mvn
RUN ./mvnw -q dependency:go-offline        # 의존성 레이어 — 소스가 바뀌어도 캐시 재사용
COPY src src
RUN ./mvnw -q package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r app && chown app /app
USER app                                   # root 로 실행하지 않는다
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

12-4. Kubernetes ⭐

컨테이너가 수백 개가 되면 어느 서버에 띄울지, 죽으면 누가 다시 띄울지, 어떻게 찾아갈지, 어떻게 무중단으로 바꿀지가 문제가 된다. 쿠버네티스는 이를 자동화하는 컨테이너 오케스트레이터다.

핵심 원리 — 선언적 구성과 조정 루프: "레플리카 3개"라는 원하는 상태를 선언하면, 컨트롤러가 현재 상태를 계속 관찰하며 차이를 메운다. 하나가 죽으면 새로 띄운다(자가 치유).

우아한 종료SIGTERM → 유예 시간 → SIGKILL. 애플리케이션이 SIGTERM 을 처리해야 요청이 끊기지 않는다

12-7. 관측성 · 장애 대응 🔥 🧮

모니터링 vs 관측성

모니터링은 미리 정한 지표가 임계값을 넘는지 본다("무엇이 고장 났는가"). 관측성은 시스템이 내놓는 신호로부터 처음 보는 문제의 원인까지 물을 수 있는 성질이다("왜 고장 났는가").

신호내용답하는 질문도구 예
메트릭시간에 따른 숫자 (집계)얼마나? 언제부터?Prometheus, Grafana
로그개별 사건의 기록정확히 무슨 일이?ELK, Loki
트레이스요청 하나가 서비스들을 거친 경로와 구간별 시간어디서 느린가?OpenTelemetry, Jaeger

4대 황금 신호: 지연 시간(Latency), 트래픽(Traffic), 오류율(Errors), 포화도(Saturation — 자원이 얼마나 찼는가)

SLI · SLO · SLA

용어뜻예
SLI (지표)서비스 수준을 측정한 값성공한 요청의 비율
SLO (목표)내부적으로 정한 목표치30일 기준 성공률 99.9%
SLA (협약)고객과의 계약. 어기면 보상99.5% 미만이면 요금 환불
오류 예산1 − SLO. 허용된 실패량99.9% → 0.1%
  • 오류 예산이 남아 있으면 새 기능을 빠르게 내고, 다 쓰면 안정화에 집중한다. "얼마나 안전하게 할 것인가"를 숫자로 합의하는 장치다.

가용성 계산

가용성연간 허용 중단월간 허용 중단
99%3.65일7.3시간
99.9%8.76시간43.8분
99.99%52.6분4.38분
99.999%5.26분26.3초

가용성 = MTBF / (MTBF + MTTR) — MTBF(평균 고장 간격)를 늘리거나 MTTR(평균 복구 시간)을 줄이면 오른다.

예제. 가용성이 각각 99% 인 구성 요소 두 개를 (1) 직렬로 (2) 병렬(이중화)로 연결했을 때의 가용성은? (3) 웹(99.9%) → 애플리케이션(99.9%) → DB(99.9%) 를 거치는 서비스의 가용성과 연간 중단 시간은?

풀이
  1. 직렬: 둘 다 살아 있어야 한다 → 0.99 × 0.99 = 98.01%
  2. 병렬: 둘 다 죽어야 중단 → 1 − (0.01 × 0.01) = 99.99%
  3. 0.999³ ≈ 99.7% → 연간 약 0.3% × 8,760시간 ≈ 26시간

거치는 구성 요소가 늘수록 전체 가용성은 내려가고, 이중화하면 올라간다. 그래서 단일 장애점(SPOF)을 찾아 이중화한다.

좋은 알림의 조건

  • 증상 기준으로 알린다(사용자가 겪는 오류율·지연). 원인 지표(CPU 80%)마다 알리면 알림 피로가 쌓여 진짜 알림을 놓친다.
  • 알림을 받은 사람이 무엇을 해야 하는지 알 수 있어야 한다(런북 링크).
  • 지금 사람이 움직여야 하는 것만 호출하고, 나머지는 티켓이나 대시보드로 보낸다.

장애 대응

단계내용
1. 탐지알림, 고객 문의. 탐지가 늦을수록 피해가 커진다
2. 전파 · 역할 분담지휘자, 조치 담당, 소통 담당을 나눈다. 상황을 한 채널에 기록
3. 완화원인 규명보다 서비스 복구가 먼저. 롤백, 트래픽 전환, 기능 끄기, 증설
4. 원인 분석로그·지표·변경 이력 확인. "최근에 무엇이 바뀌었는가"가 가장 강력한 단서
5. 복구 확인지표가 정상으로 돌아왔는지, 밀린 작업은 없는지
6. 사후 검토시간순 기록, 근본 원인, 잘된 점·부족한 점, 재발 방지 조치와 담당·기한
  • 비난 없는 사후 검토(Blameless Postmortem): 개인의 실수가 아니라 실수가 장애로 이어지게 둔 시스템·절차를 고친다. 탓하면 다음부터 숨긴다.
  • 5 Whys: "왜?"를 거듭 물어 표면 원인 뒤의 구조적 원인까지 내려간다.
  • 대부분의 장애는 변경(배포, 설정, 인프라 작업)에서 시작된다. 그래서 점진적 배포, 빠른 롤백, 변경 이력 추적이 핵심 방어 수단이다.
