블랙박스 테스트 기법

🔥 블랙박스 테스트 기법 (3가지 이상)

기법 설명
동등 분할 (Equivalence Partitioning) 입력 값의 범위를 동일하게 처리될 것으로 예상되는 그룹(클래스) 으로 나누고, 각 그룹에서 대표값 하나씩만 테스트
경계값 분석 (Boundary Value Analysis) 오류가 경계(최소/최대값 근처)에서 집중적으로 발생한다는 경험에 기반해, 경계값과 그 바로 안팎 값을 집중 테스트
결정 테이블 (Decision Table) 테스트 여러 조건의 조합에 따른 결과를 표로 정리하여, 모든(또는 주요) 조합에 대한 테스트 케이스 도출
상태 전이 (State Transition) 테스트 시스템이 특정 상태(State) 를 가질 때, 이벤트에 따른 상태 전이가 올바른지 검증
유스케이스(Use Case) 테스트 사용자의 실제 업무 시나리오 흐름대로 테스트

결합도(Coupling) · 응집도(Cohesion) 🔥

결합도 (Coupling) 응집도 (Cohesion)
정의 모듈 간 상호 의존 정도 모듈 내부 요소들이 하나의 기능을 위해 뭉친 정도
바람직한 방향 낮을수록 좋음 높을수록 좋음 
결합도 (약 → 강, 좋음 → 나쁨)
  자료 < 스탬프 < 제어 < 외부 < 공통 < 내용
  (암기: 자스제외공내)

응집도 (강 → 약, 좋음 → 나쁨)
  기능적 > 순차적 > 교환(통신)적 > 절차적 > 시간적 > 논리적 > 우연적
  (암기: 기순교절시논우)
  • 자료 결합도(Data Coupling): 모듈 간에 필요한 데이터(단순 값)만 매개변수로 주고받는 가장 느슨한 결합. 예: add(int a, int b)
  • 기능적 응집도(Functional Cohesion): 모듈 안의 모든 요소가 단 하나의 기능 수행에 기여하는 가장 강한 응집. 예: calculateTax() 하나만 하는 모듈
  • 모듈화의 목표: 결합도는 낮추고 응집도는 높인다 → 한 모듈의 변경이 다른 모듈로 퍼지지 않고(변경 파급 최소화), 모듈을 독립적으로 이해·테스트·재사용할 수 있다
  • 연결: MVC(관심사 분리), SOLID의 단일 책임 원칙(SRP)

ACID 🔥

특성 의미 보장 장치
원자성 (Atomicity) 모두 반영되거나 전혀 반영되지 않음 (All or Nothing) 회복 기법 Undo
일관성 (Consistency) 실행 전후 DB가 무결성 제약을 만족하는 일관된 상태 유지 무결성 제약조건 (+ 올바른 트랜잭션 설계)
격리성 (Isolation) 동시에 실행되는 트랜잭션은 서로의 중간 결과를 볼 수 없음 동시성 제어 (로킹 등)
지속성 (Durability) 커밋된 결과는 장애가 나도 영구 보존 회복 기법 Redo, 로그

ACID는 트랜잭션의 특성이고, DBMS가 회복 기법과 동시성 제어로 이를 보장한다. 일관성만은 DBMS 혼자가 아니라 트랜잭션 설계와 함께 보장된다. Redo/Undo는 8-4 참고.

SQL 뼈대 코드

-- 1. 조회 (쓰는 순서)
SELECT 열, 집계함수(열) AS 별칭
FROM 테이블 A
  [INNER | LEFT OUTER] JOIN 테이블 B ON A.키 = B.키
WHERE 행 조건
GROUP BY 열
HAVING 그룹 조건
ORDER BY 열 [ASC | DESC];
-- 실행 순서: FROM → (JOIN) → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

-- 2. 삽입
INSERT INTO 테이블 (열1, 열2) VALUES (값1, 값2);
INSERT INTO 테이블 (열1, 열2) SELECT …;          -- 조회 결과로 삽입

-- 3. 수정 (FROM 없음)
UPDATE 테이블 SET 열1 = 값1, 열2 = 값2 WHERE 조건;

-- 4. 삭제 (DELETE * 아님)
DELETE FROM 테이블 WHERE 조건;

-- 5. 구조 변경 (DDL)
CREATE TABLE 테이블 (열 타입 [NOT NULL], …, PRIMARY KEY (열), FOREIGN KEY (열) REFERENCES 부모(열));
ALTER TABLE 테이블 ADD 열 타입;                 -- 열 추가
ALTER TABLE 테이블 MODIFY 열 새타입;            -- 타입 변경 (SQL Server: ALTER COLUMN)
ALTER TABLE 테이블 DROP COLUMN 열;              -- 열 삭제
ALTER TABLE 테이블 RENAME COLUMN 옛 TO 새;      -- 이름 변경
DROP TABLE 테이블;   TRUNCATE TABLE 테이블;      -- 구조째 삭제 / 데이터만 비움
CREATE VIEW 뷰 AS SELECT … [WITH CHECK OPTION];
CREATE INDEX 인덱스 ON 테이블 (열);

-- 6. 권한 부여 (DCL)
GRANT SELECT, UPDATE ON 테이블 TO 사용자 [WITH GRANT OPTION];

-- 7. 권한 회수
REVOKE SELECT ON 테이블 FROM 사용자 [CASCADE | RESTRICT];

-- 8. 트랜잭션 (TCL)
COMMIT;   ROLLBACK;   SAVEPOINT 이름;   ROLLBACK TO 이름;
분류 명령 한 줄
DDL (정의) CREATE, ALTER, DROP, TRUNCATE 구조를 만든다
DML (조작) SELECT, INSERT, UPDATE, DELETE 데이터를 다룬다
DCL (제어) GRANT, REVOKE 권한을 준다·뺏는다
TCL (트랜잭션) COMMIT, ROLLBACK, SAVEPOINT 확정·취소
  • 조회 권한은 SELECT(VIEW 아님). WHERE는 그룹 전 행 조건, HAVING은 그룹 후 집계 조건.
  • 날짜가 'YYYYMMDD' 문자열이면 = '20230821', BETWEEN '20220101' AND '20221231', LIKE '2022%'. → 오답 패턴은 8-2

🔥 Anomaly (이상 현상)

정규화가 안 된 릴레이션에서 데이터 변경 시 발생하는 3가지 이상 현상:

이상 정의 예
삽입 이상 (Insertion Anomaly) 새 데이터를 삽입하려는데, 불필요한 다른 속성 값까지 함께 입력해야만 삽입이 가능한 문제 신입생이 수강 신청 전이라 과목 정보가 없으면, 학생 정보(학번 등)조차 등록할 수 없음(과목번호가 기본키의 일부라 NULL 불가)
삭제 이상 (Deletion Anomaly) 튜플 하나를 삭제했더니, 의도치 않게 다른 유용한 정보까지 함께 삭제되는 문제 어떤 학생의 유일한 수강 기록을 삭제했더니, 그 학생이 어느 지도교수인지 정보까지 통째로 사라짐
갱신 이상 (Update Anomaly) 하나의 사실이 여러 튜플에 중복 저장되어 있어, 값을 변경할 때 일부만 수정되어 데이터 불일치가 발생하는 문제 한 지도교수의 소속 학과가 바뀌었는데, 그 교수의 학생 수만큼 반복 저장된 행 중 일부 행만 수정하면 같은 교수인데 학과가 다르게 기록되는 모순 발생

원인: 하나의 릴레이션에 여러 개의 사실(주제)이 섞여 있기 때문(정규화 미흡). → 해결책 = 정규화(Normalization)

한 마디로: 넣을 수 없다 / 지우면 같이 사라진다 / 고치다 어긋난다. 답안의 예시는 반드시 문제에 주어진 테이블의 튜플로 쓴다.

전송 지연 (Transmission) 패킷의 모든 비트를 링크로 밀어내는 시간 = L / R 패킷 길이 L, 링크 전송률 R
전파 지연 (Propagation) 비트 하나가 매체를 따라 이동하는 시간 = d / s 링크 거리 d, 전파 속도 s(빛의 속도 근처)

⚠️ 함정 — 전송 vs 전파: 전송 지연은 패킷 크기·대역폭에 비례(톨게이트를 차량 행렬이 통과하는 시간), 전파 지연은 거리에 비례(톨게이트 사이를 달리는 시간). 대역폭을 늘려도 전파 지연은 줄지 않는다. 전체 노드 지연 = 처리 + 큐잉 + 전송 + 전파 · 성능 지표: 지연(delay), 처리량(throughput = 병목 링크 전송률), 패킷 손실률

3. 헷갈리는 개념 🔥

정규화 — 1NF부터 6NF까지

함수 종속(FD) X → Y: X 값이 정해지면 Y 값이 하나로 정해진다. 정규화는 "하나의 릴레이션 = 하나의 주제"가 되도록 종속 관계를 기준으로 쪼개는 과정이다.

암기: 도 · 부 · 이 · 결 · 다 · 조 (도메인 원자값 → 부분 종속 → 이행 종속 → 결정자 → 다치 종속 → 조인 종속)

정규형 제거 대상 한 줄 조건 분해 규칙
1NF 다중값·반복 그룹 모든 속성이 원자값 다중값을 행으로 펼침
2NF 부분 함수 종속 1NF + 비키 속성이 기본키 전체에 종속 키의 일부에만 종속된 속성을 그 일부 키와 함께 분리. 기본키가 단일 속성이면 자동 만족
3NF 이행 함수 종속 2NF + 비키 속성이 다른 비키 속성에 종속되지 않음 A → B → C에서 중간 다리 B를 키로: (A, B) + (B, C)
BCNF 후보키가 아닌 결정자 모든 결정자가 후보키 그 결정자를 키로 하는 릴레이션으로 분리
4NF 다치 종속 (A →→ B) 독립적인 다중값 사실이 한 테이블에 없음 독립적인 다중값마다 분리
5NF 조인 종속 후보키를 통하지 않는 조인 종속 없음 셋 이상으로 쪼개야만 손실 없이 복원되는 경우 분해
6NF 모든 비자명 조인 종속 키 + 속성 1개까지 분해 시간 이력(Temporal) DB·DW에서 사용, 시험엔 정의만

하나의 예로 단계 따라가기 — 수강(학번, 이름, 지도교수, 학과, 과목, 성적)

단계 문제 결과
1NF 과목 칸에 "DB, OS" 같은 다중값 과목마다 행을 나눔. 기본키 = (학번, 과목)
2NF 학번 → 이름·지도교수·학과 (키의 일부에만 종속) 학생(학번, 이름, 지도교수, 학과) + 수강(학번, 과목, 성적)
3NF 학번 → 지도교수 → 학과 (이행) 학생(학번, 이름, 지도교수*) + 교수(지도교수, 학과)
BCNF 강의(학생, 과목, 교수)에서 교수 → 과목인데 교수는 후보키 아님 (학생, 교수) + (교수, 과목)
4NF 교수(교수, 강의과목, 취미): 과목과 취미가 서로 무관한 다중값 (교수, 강의과목) + (교수, 취미)
5NF 공급(공급자, 부품, 프로젝트)이 셋 중 둘씩 짝지은 세 테이블로만 정확히 복원 (공급자, 부품) + (부품, 프로젝트) + (공급자, 프로젝트)
  • 🔥 이행 종속 vs 조인 종속 혼동 금지: A → B → C는 이행(3NF). 조인 종속은 5NF.
  • 3NF 분해를 (학번, 지도교수) + (학번, 학과)로 하면 "지도교수 → 학과"가 사라져 종속성 보존 실패, 교수의 학과가 학생 수만큼 중복된 채 남는다.
  • 좋은 분해의 두 조건: 무손실 조인(다시 조인하면 원래대로) + 종속성 보존.
정규화 장점 정규화 단점
삽입·삭제·갱신 이상 제거 테이블·JOIN 증가 → 조회 성능 저하
중복 최소화 → 저장 공간 절약, 일관성 설계·쿼리 복잡도 상승
무결성 유지 용이 과하면 비효율 → 반정규화(Denormalization)로 일부 합침

순서 개념 한 줄

  • 같은 서브넷인지 판단: 두 IP를 각각 마스크와 AND → 결과(네트워크 주소)가 같으면 같은 서브넷 → 직접 전달, 다르면 기본 게이트웨이로.

DHCP (Dynamic Host Configuration Protocol) 🔥

정의: 호스트에 IP 주소·서브넷 마스크·기본 게이트웨이·DNS 서버 주소를 자동으로 임대(Lease)해 주는 응용 계층 프로토콜. UDP 사용 — 서버 67, 클라이언트 68.

필요성: 수동 설정의 오류·중복 방지, 이동 단말 자동 설정, 주소 재사용(임대 기간 만료 시 회수)으로 주소 자원 절약.

단계 방향 브로드캐스트하는 이유 🔥
DISCOVER 클라이언트 → 서버 클라이언트는 자기 IP도, DHCP 서버 주소도 모른다 → 출발지 0.0.0.0, 목적지 255.255.255.255
OFFER 서버 → 클라이언트 클라이언트에 아직 IP가 설정되지 않아 유니캐스트로 받을 수 없다
REQUEST 클라이언트 → 서버 여러 DHCP 서버가 OFFER했을 수 있으므로, 어느 서버의 제안을 수락했는지 모든 서버에 알린다 (선택받지 못한 서버는 예약 주소를 회수)
ACK 서버 → 클라이언트 클라이언트가 아직 IP 설정을 완료하지 않은 상태라 브로드캐스트로 최종 확인 전달
  • Transaction ID로 요청과 응답을 짝지음, 임대 갱신은 T1(50%) 시점 유니캐스트 REQUEST
  • △ 다른 서브넷의 DHCP 서버를 쓰려면 라우터가 브로드캐스트를 넘기지 않으므로 DHCP Relay Agent 필요

3-way vs 4-way Handshake

3-way (연결 수립) 4-way (연결 종료)
목적 양쪽 송수신 가능 확인 + ISN 교환 양쪽 방향을 각각 닫음
흐름 SYN → SYN+ACK → ACK FIN → ACK → (남은 데이터 전송) → FIN → ACK
왜 이 횟수? 서버의 SYN과 ACK를 한 세그먼트에 합칠 수 있어 3번 서버가 FIN을 받아도 보낼 데이터가 남아 있을 수 있어 ACK와 FIN을 따로 보냄 → 4번 (반이중 종료, Half-close)
상태 클라이언트 SYN_SENT → ESTABLISHED / 서버 LISTEN → SYN_RCVD → ESTABLISHED 능동 종료 측 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED / 수동 측 CLOSE_WAIT → LAST_ACK → CLOSED
관련 공격·이슈 SYN Flooding(반개방 연결로 백로그 큐 고갈) TIME_WAIT(2MSL 대기: 마지막 ACK 유실 대비, 지연 패킷 혼동 방지)

→ 그림·순서 번호는 2-3, 계산은 A-7

🔥 대응책 (웹서비스 제공자 입장)

XSS 대응 1. 입력값 검증 및 필터링(Sanitization) — <, >, ", ', & 등 특수문자와 <script> 태그를 제거·차단. 화이트리스트 방식이 블랙리스트보다 안전 2. 출력 시 이스케이프/인코딩(Output Encoding) — 출력 컨텍스트(HTML, JS, URL, CSS)에 맞게 인코딩. < → &lt;. XSS 방어의 가장 근본적 조치 3. CSP (Content Security Policy) 헤더 적용 — 신뢰할 수 있는 출처의 스크립트만 실행 허용, 인라인 스크립트 차단 4. 쿠키에 HttpOnly 속성 설정 — JavaScript(document.cookie)로 쿠키에 접근할 수 없게 하여 세션 탈취를 원천 차단 5. 검증된 라이브러리·프레임워크 사용(React, Vue 등은 기본적으로 이스케이프 처리)

CSRF 대응 1. CSRF 토큰 사용 — 서버가 폼마다 예측 불가능한 난수 토큰을 발급하고, 요청 시 함께 받아 검증. 공격자는 이 토큰 값을 알 수 없다. 가장 표준적인 방어 2. 쿠키에 SameSite 속성 설정 — SameSite=Strict 또는 Lax로 설정하면 외부 사이트에서 발생한 요청에는 쿠키가 첨부되지 않는다 3. Referer / Origin 헤더 검증 — 요청 출처가 자사 도메인인지 확인 4. 중요 작업에 재인증 요구 — 비밀번호 재입력, OTP, CAPTCHA 5. HTTP 메서드 준수 — 상태를 변경하는 작업은 GET이 아닌 POST/PUT/DELETE로 처리 (GET은 <img> 태그만으로 유발 가능)

한 문장 구별법: XSS는 "사용자를 속여 스크립트를 실행시키는" 공격, CSRF는 "사용자의 권한을 빌려 서버에 요청을 보내는" 공격이다. XSS는 입력/출력 처리 문제, CSRF는 요청 출처 검증 문제다.

Spinlock vs Mutex vs Semaphore

🔥 비교표: Mutex vs Semaphore vs Spinlock

항목 Mutex Semaphore Spinlock
개념 상호 배제를 위한 락(Lock) 사용 가능한 자원 개수를 세는 정수 변수 바쁜 대기(Busy Waiting) 를 하는 락
값의 범위 0 또는 1 (이진) 0 ~ N (계수형) / 1 (이진) 0 또는 1
소유권 ✅ 있음 — 락을 건 스레드만 해제 가능 ❌ 없음 — 누구나 signal() 가능 ✅ 있음
대기 방식 Sleep (Blocked 상태로 전환, CPU 반납) Sleep (일반적 구현) Busy Waiting (while 루프로 계속 확인, CPU 점유)
Context Switch 발생 발생 발생하지 않음
주 용도 하나의 공유 자원 보호 N개 자원 관리, 실행 순서 제어 짧은 임계 구역, 멀티코어
단점 전환 오버헤드 잘못 쓰면 교착 상태 유발 대기 중 CPU 낭비

핵심 구별 질문 - "락을 건 주체만 풀 수 있는가?" → Mutex는 Yes, Semaphore는 No (소유권 유무가 가장 확실한 구별점) - "자원이 여러 개인가?" → Counting Semaphore - "실행 순서를 강제하는가?" (A가 끝난 뒤 B 실행) → Semaphore

고르는 기준

  • 임계 구역이 짧고 멀티코어 → 스핀락 (잠들었다 깨는 문맥 교환 비용 > 잠깐 도는 비용)
  • 임계 구역이 길다 → 뮤텍스
  • 자원이 여러 개이거나 실행 순서를 강제 → 세마포어
  • 🔥 스핀락을 잡은 상태에서는 잠들면 안 된다 → 그 안에서 또 락이 필요하면 스핀락. 실전 문제는 2024 시나리오

5. 상호 배제 코드 — Mutex · Semaphore 🔥

모든 예제는 같은 문제를 푼다: 작업자 3개가 공유 카운터를 1000번씩 올린다. 락이 없으면 counter = counter + 1(읽기 → 더하기 → 쓰기)이 섞여 결과가 3000보다 작게 나올 수 있다(경쟁 상태).

언어 상호 배제(1개) 카운팅 세마포어(N개)
C — 프로세스(fork) 이진 세마포어 sem_open(…, 1) sem_open(…, N)
C — 스레드(pthread) pthread_mutex_lock / unlock sem_init(&s, 0, N), sem_wait / sem_post
C++ std::mutex + std::lock_guard std::counting_semaphore<N>, acquire / release

C — fork로 자식 여러 개 + POSIX 세마포어

// gcc sem_fork.c -o sem_fork -pthread
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <semaphore.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

int *make_shared_counter(void);               // 아래에 정의 (부모·자식이 함께 보는 메모리)
void child_work(int *counter, sem_t *lock);   // 아래에 정의 (자식이 하는 일)

int main(void) {
    int *counter = make_shared_counter();
    // 이름 있는 세마포어: 서로 다른 프로세스가 같은 이름으로 같은 세마포어를 공유
    // 초기값 1 → 동시에 1개만 통과 = 뮤텍스처럼 동작 (이진 세마포어)
    sem_t *lock = sem_open("/counter_lock", O_CREAT, 0644, 1);

    for (int i = 0; i < 3; i++) {
        pid_t pid = fork();
        if (pid == 0) {              // 자식만 들어오는 블록 (fork는 자식에게 0을 반환)
            child_work(counter, lock);
            exit(0);                 // 🔥 자식은 여기서 끝낸다. 없으면 자식도 for를 계속 돌며
                                     //    또 fork → 3번 반복에 프로세스 2^3 = 8개가 생긴다
        }
        // 부모는 pid > 0 을 받고 다음 자식을 만들러 반복
    }

    for (int i = 0; i < 3; i++) {
        wait(NULL);                  // 자식 3개를 모두 회수 (좀비 방지, 출력 순서 보장)
    }
    printf("counter = %d\n", *counter);   // 항상 3000

    sem_close(lock);
    sem_unlink("/counter_lock");     // 이름 제거 (안 하면 다음 실행 때 남아 있음)
    return 0;
}

void child_work(int *counter, sem_t *lock) {
    for (int k = 0; k < 1000; k++) {
        sem_wait(lock);              // P 연산: 값이 0이면 대기, 아니면 1 감소하고 통과
        *counter = *counter + 1;     // 임계 구역
        sem_post(lock);              // V 연산: 1 증가, 기다리던 프로세스 하나를 깨움
    }
}

int *make_shared_counter(void) {
    // fork 후 일반 변수는 부모·자식이 각자 복사본을 가진다(Copy-On-Write).
    // MAP_SHARED 메모리여야 모든 프로세스가 같은 counter를 본다.
    int *p = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    *p = 0;
    return p;
}
  • 🔥 fork 뒤의 일반 전역 변수는 공유되지 않는다(각자 복사본). 프로세스 간에는 공유 메모리 + 이름 있는 세마포어가 필요하다.

C — pthread 뮤텍스와 카운팅 세마포어

// gcc thread_lock.c -o thread_lock -pthread
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>

int counter = 0;                                   // 스레드끼리는 전역 변수를 그대로 공유
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
sem_t slots;                                       // 동시에 들어갈 수 있는 자리 수

void *worker(void *arg);                           // 아래에 정의
void *limited_worker(void *arg);                   // 아래에 정의

int main(void) {
    pthread_t t[3];

    // ① 뮤텍스: 한 번에 1개
    for (int i = 0; i < 3; i++) pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);    // 스레드 종료 대기 (프로세스의 wait에 해당)
    printf("counter = %d\n", counter);                       // 3000

    // ② 카운팅 세마포어: 한 번에 최대 2개
    sem_init(&slots, 0, 2);          // 두 번째 인자 0 = 같은 프로세스의 스레드끼리 공유
    for (int i = 0; i < 3; i++) pthread_create(&t[i], NULL, limited_worker, NULL);
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    sem_destroy(&slots);
    return 0;
}

void *worker(void *arg) {
    for (int k = 0; k < 1000; k++) {
        pthread_mutex_lock(&m);      // 잠근 스레드만 풀 수 있다 (소유권)
        counter = counter + 1;
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

void *limited_worker(void *arg) {
    sem_wait(&slots);                // 자리가 0이면 대기
    printf("작업 중 (최대 2개 동시)\n");
    sem_post(&slots);                // 자리 반납 — 다른 스레드가 해도 됨 (소유권 없음)
    return NULL;
}

C++ — std::mutex, std::counting_semaphore

// g++ -std=c++20 lock.cpp -o lock -pthread
#include <iostream>
#include <mutex>
#include <semaphore>
#include <thread>
#include <vector>

int counter = 0;
std::mutex m;
std::counting_semaphore<2> slots(2);   // 최대 2개 동시

void worker();                          // 아래에 정의
void limited_worker();                  // 아래에 정의

int main() {
    std::vector<std::thread> ts;
    for (int i = 0; i < 3; i++) ts.emplace_back(worker);
    for (auto &t : ts) t.join();
    std::cout << "counter = " << counter << "\n";   // 3000

    std::vector<std::thread> ls;
    for (int i = 0; i < 3; i++) ls.emplace_back(limited_worker);
    for (auto &t : ls) t.join();
}

void worker() {
    for (int k = 0; k < 1000; k++) {
        std::lock_guard<std::mutex> guard(m);   // 생성 시 lock, 블록을 벗어나면 자동 unlock (RAII)
        counter = counter + 1;                  // 예외가 나도 unlock이 보장됨
    }
}

void limited_worker() {
    slots.acquire();     // P
    std::cout << "작업 중\n";
    slots.release();     // V
}

Java — synchronized, ReentrantLock, Semaphore

import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;

public class LockDemo {
    public static void main(String[] args) throws InterruptedException {
        Counter c = new Counter();
        Thread[] ts = new Thread[3];
        for (int i = 0; i < 3; i++) {
            ts[i] = new Thread(() -> {
                for (int k = 0; k < 1000; k++) c.increase();
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();            // 스레드 종료 대기
        System.out.println("counter = " + c.get());   // 3000

        Pool pool = new Pool();
        for (int i = 0; i < 3; i++) new Thread(pool::use).start();
    }
}

class Counter {
    private int value = 0;
    private final ReentrantLock lock = new ReentrantLock();

    // 방법 1: synchronized — 메서드에 진입할 때 이 객체의 모니터 락을 얻는다
    synchronized void increase() {
        value = value + 1;
    }

    // 방법 2: ReentrantLock — 직접 잠그고, 예외가 나도 풀리도록 finally에서 unlock
    void increaseWithLock() {
        lock.lock();
        try {
            value = value + 1;
        } finally {
            lock.unlock();
        }
    }

    synchronized int get() { return value; }
}

class Pool {
    private final Semaphore slots = new Semaphore(2);   // 최대 2개 동시

    void use() {
        try {
            slots.acquire();          // P (InterruptedException 가능)
            try {
                System.out.println(Thread.currentThread().getName() + " 작업 중");
            } finally {
                slots.release();      // V
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

생산자-소비자 (세마포어 3개)

세마포어 초기값 의미
mutex 1 버퍼 접근 상호 배제
empty N 빈 칸 수
full 0 찬 칸 수 
// 생산자
sem_wait(&empty);    // 빈 칸이 생길 때까지 대기
sem_wait(&mutex);
buffer[in] = item;  in = (in + 1) % N;
sem_post(&mutex);
sem_post(&full);     // 찬 칸 +1 → 소비자를 깨움

// 소비자
sem_wait(&full);     // 찬 칸이 생길 때까지 대기
sem_wait(&mutex);
item = buffer[out];  out = (out + 1) % N;
sem_post(&mutex);
sem_post(&empty);    // 빈 칸 +1 → 생산자를 깨움
  • 🔥 wait 순서를 바꾸면(mutex를 먼저) 교착: 버퍼가 가득 찼을 때 생산자가 mutex를 쥔 채 empty를 기다리면, 소비자는 mutex를 못 얻어 칸을 비울 수 없다.
  • 세마포어의 두 용도: 상호 배제(초기값 1) / 순서 제어(초기값 0 — "A가 끝나야 B 실행": A 끝에 post, B 앞에 wait).
