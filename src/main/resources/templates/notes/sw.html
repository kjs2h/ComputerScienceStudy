7-1. 개발 방법론 🔥

Waterfall vs Agile

항목 Waterfall (폭포수) Agile (애자일)
진행 방식 순차적(요구분석→설계→구현→테스트→유지보수), 이전 단계로 되돌아가지 않음(원칙상) 반복적·점증적(Iteration/Sprint 단위로 짧게 반복)
요구사항 초기에 완전히 확정되어야 함 변화하는 요구사항을 수용(Agile 선언문의 핵심 가치)
산출물 우선순위 문서화 중시 동작하는 소프트웨어 중시
고객 참여 초기·말기에 제한적 매 반복마다 지속적 참여·피드백
장점 단계별 산출물 명확, 진행 상황 파악 쉬움, 관리 용이 변화 대응력 높음, 빠른 피드백, 조기 가치 제공
단점 요구사항 변경에 취약(뒤늦게 발견된 결함 수정 비용 큼), 실제 동작하는 결과물을 늦게 확인 문서화 부족 우려, 전체 일정·비용 예측 어려움, 숙련된 팀 필요
적합한 상황 요구사항이 명확하고 안정적인 대규모/공공 프로젝트 요구사항이 변화하는 스타트업/신사업

핵심 한 줄: Waterfall은 "계획대로"를 우선하고, Agile은 "변화 대응"을 우선한다.

🔥 V모델 (빈칸 채우기)

정의: Waterfall 모델의 변형으로, 각 개발(설계) 단계가 어떤 테스트 단계와 대응하는지를 V자 형태로 명시적으로 보여주는 모델.

    요구분석                          인수 테스트
       │                                  ▲
       ▼                                  │
   ① 시스템 설계 ────────────────────► 시스템 테스트
   (System Design)                        ▲
       │                                  │
       ▼                                  │
   ② 상세 설계 ─────────────────────► 통합 테스트
   (Detailed Design)                      ▲
       │                                  │
       ▼                                  │
      구현 ───────────────────────────► 단위 테스트
빈칸 정답 설명
① 시스템 설계 (Architecture/System Design) 시스템 전체 구조, 모듈 간 관계를 설계 → 이후 시스템 테스트와 대응
② 상세 설계 (Detailed Design) 개별 모듈·컴포넌트 내부 로직을 설계 → 이후 통합 테스트와 대응

단위 테스트 vs 통합 테스트가 수행하는 검증 내용

테스트 대응 설계 단계 검증 내용
단위 테스트 (Unit Test) 구현(코드) 개별 함수·메서드·클래스 등 최소 단위가 명세대로 동작하는지 독립적으로 검증
통합 테스트 (Integration Test) 상세 설계 단위 테스트를 통과한 모듈들을 서로 결합했을 때 인터페이스가 올바르게 상호작용하는지 검증(모듈 간 데이터 전달, 호출 관계 등)

V모델의 의의: 왼쪽(설계)에서 결정한 내용이 오른쪽(테스트)에서 검증 기준(Test Case)의 근거가 된다는 것을 시각적으로 보여준다 → 테스트를 개발 초기부터 함께 계획하게 만들어, Waterfall의 "결함을 늦게 발견하는" 단점을 일부 보완한다.

7-2. 테스트 🔥

블랙박스 테스트 vs 화이트박스 테스트

블랙박스 테스트 화이트박스 테스트
관점 내부 구조를 모른 채 입력과 출력만으로 검증 내부 코드 로직·구조를 보면서 검증
기준 명세(요구사항) 코드 커버리지(구문/분기/조건)
수행 주체 주로 QA, 사용자 관점 주로 개발자

↗ 요약 페이지 · 블랙박스 테스트 기법 (3가지 이상)

🔥 Test Oracle

정의: 테스트를 실행한 후, 그 결과가 옳은지 그른지를 판단하기 위한 기준(참值, 예상 결과). 프로그램의 실제 출력과 비교할 "정답"을 제공하는 메커니즘.

필요성: 아무리 테스트 케이스를 잘 만들어도, 결과가 맞는지 판단할 기준이 없으면 테스트는 무의미하다. Test Oracle이 이 "판단 기준"을 제공한다.

유형

유형 설명
True Oracle 모든 입력에 대해 완벽하게 정확한 결과를 제공(이상적이나 현실적으로 구현 어려움)
Sampling Oracle 일부 입력에 대해서만 정확한 결과 제공
Heuristic Oracle Sampling Oracle을 보완하여, 나머지 입력은 추정 규칙으로 결과 판단
Consistent Oracle 이전 실행 결과와 일관성이 있는지만 비교(회귀 테스트에 활용)

🔥 Alpha 테스트 vs Beta 테스트

Alpha 테스트 Beta 테스트
수행 장소 개발사 내부(통제된 환경) 실사용 환경(고객/사용자의 실제 환경)
수행 주체 내부 QA, 일부 초청된 사용자 불특정 다수의 실사용자

목적 주요 결함을 출시 전 미리 발견 다양한 실사용 환경·시나리오에서의 결함, 사용성 피드백 수집
시점 Beta보다 먼저 Alpha 이후, 정식 출시 직전

7-3. 객체지향(OOP) 🔥

캡슐화 / 상속 / 다형성

개념 정의 목적/효과
캡슐화 (Encapsulation) 데이터(속성)와 그 데이터를 다루는 메서드를 하나로 묶고, 외부에는 필요한 인터페이스만 공개(정보 은닉) 내부 구현 변경이 외부에 영향 안 줌, 데이터 무결성 보호
상속 (Inheritance) 기존 클래스(부모/상위)의 속성과 메서드를 새 클래스(자식/하위)가 물려받아 재사용하고 확장 코드 재사용성, 계층적 분류, 유지보수 용이
다형성 (Polymorphism) 동일한 인터페이스(메서드 호출) 가 객체의 실제 타입에 따라 다르게 동작하는 성질 유연하고 확장 가능한 설계(예: 여러 도형 클래스가 각자 다른 draw() 구현)

🔥 오버로딩 vs 오버라이딩

오버로딩 (Overloading) 오버라이딩 (Overriding)
발생 위치 같은 클래스 내 상속 관계(부모-자식 클래스)
조건 메서드 이름은 같고 매개변수의 개수·타입이 다름 메서드 이름·매개변수·반환타입이 완전히 동일
반환 타입 오버로딩 성립에 영향 없음(다를 수 있음) 동일하거나 공변 반환타입만 허용
바인딩 시점 컴파일 타임(정적 바인딩) 런타임(동적 바인딩)
목적 동일 기능을 다양한 입력 형태로 제공 부모 클래스의 동작을 자식 클래스가 재정의
다형성과의 관계 컴파일 타임 다형성 런타임 다형성(다형성의 핵심 구현 메커니즘)
예시 add(int,int) / add(double,double) Animal.sound() → Dog.sound()가 재정의

클래스 vs 객체

클래스 (Class) 객체 (Object)
정의 객체를 만들기 위한 설계도/틀(속성과 메서드의 정의) 클래스로부터 실제로 메모리에 생성된 인스턴스
존재 개념적(정적) 실체적(동적, 런타임에 존재)
관계 하나의 클래스로 여러 개의 객체 생성 가능 각 객체는 독립적인 상태(필드 값) 보유

🔥 Java String == 비교

String str1 = new String("컴퓨터");
String str2 = new String("컴퓨터");
if(str1 == str2) System.out.println("일치");
else System.out.println("불일치");

실행 결과: 불일치

이유

new String(...)으로 생성하면 Java의 String Constant Pool(문자열 상수 풀)을 사용하지 않고, Heap 영역에 매번 새로운 String 객체를 강제로 생성한다. == 연산자는 객체의 참조(메모리 주소)를 비교하는 연산자이므로, str1과 str2는 내용("컴퓨터")은 같지만 Heap 상의 서로 다른 주소를 가리키는 별개의 객체다. 따라서 str1 == str2는 false가 되어 "불일치"가 출력된다.

만약 String str1 = "컴퓨터"; 처럼 리터럴로 생성했다면, Java는 이를 Constant Pool에서 관리하여 동일한 내용의 리터럴은 하나의 객체를 공유(재사용) 하므로 str1 == str2가 true가 됐을 것이다.

내용 비교를 하려면 ==이 아니라 .equals() 메서드를 사용해야 한다.

🔥 생성자 상속 체이닝 실행 순서

class Parent{
    Parent(){ System.out.println("Parent 1"); }
    Parent(String str){ System.out.println("Parent 2"); }
}
class Child1 extends Parent{
    Child1(){ System.out.println("Child 1"); }
}
class Child2 extends Parent{
    Child2(String str){ System.out.println("Child 2"); }
}
class FamilyTest{
    public static void main(String[] args){
        Child1 c1 = new Child1();
        Child2 c2 = new Child2("a");
    }
}

실행 결과

Parent 1
Child 1
Parent 1
Child 2

이유

Java에서 자식 클래스의 생성자는, 본문 첫 줄에 명시적으로 super(...)를 호출하지 않으면 컴파일러가 자동으로 부모의 기본 생성자(매개변수 없는 생성자)를 호출하는 super()를 암묵적으로 삽입한다.

  • Child1()은 super()를 명시하지 않았으므로 암묵적으로 Parent()(매개변수 없는 것) 가 먼저 실행 → "Parent 1" 출력 → 이어서 "Child 1" 출력
  • Child2(String str)도 마찬가지로 super()를 명시하지 않았다. 주의: Child2가 String을 받는다고 해서 Parent(String str)이 호출되는 것이 아니다. 매개변수와 무관하게 암묵적 super()는 항상 부모의 "기본 생성자" 를 호출한다 → "Parent 1" 출력 → 이어서 "Child 2" 출력

핵심 함정: Child2(String str)을 보고 Parent(String str)이 호출될 거라 착각하기 쉽다. 매개변수가 있는 부모 생성자를 호출하려면 자식 생성자에서 super(str)을 명시적으로 작성해야 한다. 이 코드는 그렇게 하지 않았으므로 두 경우 모두 Parent()(무인자)가 호출된다.

7-4. 설계 원칙 & 패턴 ⭐

↗ 요약 페이지 · SOLID 원칙

🔥 Singleton 패턴

정의: 클래스의 인스턴스가 오직 하나만 생성되도록 보장하고, 어디서든 그 하나의 인스턴스에 전역적으로 접근할 수 있게 하는 생성 패턴(Creational Pattern).

구현 핵심: 생성자를 private으로 막아 외부에서 new로 직접 생성 못 하게 하고, 클래스 내부에 유일한 인스턴스를 담는 static 필드와, 그것을 반환하는 static 메서드(getInstance())를 둔다.

사용 이유: DB 연결 풀, 설정(Config) 객체, 로그 관리자처럼 애플리케이션에 단 하나만 존재해야 하며, 자원 소모가 큰 객체를 반복 생성하지 않고 재사용하기 위해.

주의점(단점): 멀티스레드 환경에서 동시에 getInstance()를 호출하면 인스턴스가 2개 생성될 수 있어 동기화(synchronized) 처리가 필요하다. 전역 상태를 가지므로 단위 테스트가 어려워지고 결합도가 높아질 수 있다.

기타 생성 패턴 (참고) △: Factory Method(객체 생성을 서브클래스에 위임), Builder(복잡한 객체를 단계적으로 생성), Prototype(기존 객체를 복제)

주요 디자인 패턴 분류 △

분류 목적 예
생성(Creational) 객체 생성 방식 캡슐화 Singleton, Factory, Builder
구조(Structural) 클래스/객체의 조합 Adapter, Decorator, Facade, Proxy
행위(Behavioral) 객체 간 책임 분배·상호작용 Observer, Strategy, Iterator, State

MVC (Model-View-Controller) 패턴 🔥

등장 배경: 화면(UI) 코드와 데이터·비즈니스 로직이 한 덩어리면, 화면만 바꿔도 로직을 고쳐야 하고 분업도 어렵다 → 관심사의 분리(Separation of Concerns).

구성 역할 코드에서 판별하는 근거
Model 데이터와 상태(+비즈니스 로직) 필드 + getter/setter만 있음, 출력·흐름 제어 없음
View 사용자에게 보여주는 표현 System.out/화면 렌더링만, 데이터를 소유하지 않고 매개변수로 받은 값을 표시
Controller 요청을 받아 Model을 갱신하고, Model 값을 View에 전달 Model과 View의 참조를 필드로 둘 다 가짐, 둘을 중개하는 메서드 
사용자 ──요청──▶ Controller ──갱신/조회──▶ Model
                    │                         │
                    └──── 값 전달 ──▶ View ◀──┘ (구현에 따라 View가 Model 관찰)

판별 요령: 필드(상태)만 있으면 Model, 출력만 하면 View, 다른 두 객체를 필드로 들고 연결하면 Controller.

관점 MVC의 장점
Front-end View가 로직과 분리 → 화면 디자인 변경·새 View(웹/모바일) 추가 시 Model·Controller 수정 불필요, 하나의 Model을 여러 View가 재사용
Back-end Model(데이터·로직)이 화면과 독립 → UI가 바뀌어도 로직 재사용, UI 없이 단위 테스트 가능
공통 역할별 병렬 개발(분업), 낮은 결합도·높은 응집도 → 유지보수·확장 용이
  • 단점: Controller 비대화(Massive Controller), 작은 프로그램엔 구조가 과함
  • △ 변형: MVP, MVVM, Spring MVC(DispatcherServlet = Front Controller)

코드 실행 결과 추적 함정: main의 data와 Controller 안의 data가 같은 객체를 참조하면, Controller의 setter로 값을 바꾼 뒤 출력에 바뀐 값이 반영된다(Java는 참조값을 값으로 전달). 출력 문자열(구분선의 대시 개수 등)은 코드에 적힌 그대로 옮겨 쓴다.

7-5. 코드 품질 ⭐

🔥 리팩토링 (Refactoring)

정의: 소프트웨어의 겉으로 드러나는 동작(기능)은 그대로 유지하면서, 내부 코드의 구조를 개선하는 작업.

핵심 특징 - 기능적 변경이 없다 — 리팩토링 전후로 프로그램의 입출력 결과는 동일해야 함(이 점이 버그 수정·기능 추가와의 결정적 차이) - 목적: 가독성 향상, 유지보수성 향상, 중복 제거, 복잡도 감소 - 안전하게 수행하려면 테스트 코드(회귀 테스트)가 뒷받침되어야 한다(리팩토링 전후로 테스트가 계속 통과하는지로 "동작 유지"를 검증) - 예: 긴 메서드를 여러 개로 쪼개기, 중복 코드 제거, 매직 넘버를 상수로 치환, 조건문을 다형성으로 대체

Clean Code / TDD △

  • Clean Code: 읽기 쉽고, 의도가 명확하며, 다른 개발자가 쉽게 이해·수정할 수 있는 코드. 의미 있는 이름, 작은 함수, 중복 제거 등을 지향
  • TDD (Test-Driven Development): 테스트 코드를 먼저 작성한 뒤 그 테스트를 통과하는 최소한의 코드를 작성하는 개발 방식. Red(실패하는 테스트 작성) → Green(통과하는 최소 코드 작성) → Refactor(개선) 사이클 반복

🔥 오픈소스 활용 시 주의사항 (3가지)

주의사항 설명
① 라이선스 검토 GPL처럼 파생 저작물에 대한 소스 공개 의무(Copyleft) 가 있는 라이선스를 상용/폐쇄 소스 프로젝트에 무심코 포함하면 법적 분쟁·소스 공개 강제 위험이 있다. MIT/Apache처럼 상대적으로 자유로운 라이선스와 반드시 구분해야 함
② 보안 취약점 관리 오픈소스는 누구나 코드를 볼 수 있어 취약점도 공개적으로 알려지기 쉽다. 사용 중인 오픈소스의 버전과 알려진 CVE(취약점)를 지속적으로 추적하고, 패치가 적시에 반영되는지 점검해야 함(SCA, Software Composition Analysis 도구 활용)
③ 유지보수 및 지속가능성 오픈소스 프로젝트가 개발이 중단(abandoned) 되거나 커뮤니티가 비활성화될 위험이 있다. 이 경우 보안 패치·버그 수정을 기대할 수 없어 직접 포크하여 유지보수하거나 대체 라이브러리를 찾아야 하는 부담이 생긴다

(추가로 언급 가능: 공급망 공격(Supply Chain Attack) 위험, 코드 품질·문서화 수준 편차, 라이선스 호환성 충돌(서로 다른 오픈소스 조합 시))

7-6. 형상관리 (SCM) · 버전관리 도구 🔥

정의: 형상관리(Software Configuration Management)란 소프트웨어 개발 과정의 산출물(소스, 문서 등) 변경을 식별·통제·추적하는 활동이다.

  • 절차 ⭐: 형상 식별 → 형상 통제(CCB, 변경 통제 위원회 승인) → 형상 감사 → 형상 기록(상태 보고)
버전관리 도구의 기능 장점
① 버전(이력) 관리 — 변경 내용·작성자·시점 기록 변경 이력 추적, 책임 소재 명확
② 롤백 — 이전 버전으로 복원 장애 시 빠른 복구
③ 브랜치·병합(Merge) — 독립 작업 후 합침 여러 명이 동시에 개발 (협업)
④ 충돌(Conflict) 감지 — 같은 부분 동시 수정 경고 덮어쓰기 사고 방지
⑤ 비교(diff) — 버전 간 차이 표시 코드 리뷰·배포 버전 관리

⚠️ 함정 (실제 오답): 기능을 add, commit, push처럼 Git 명령어로 나열하지 말 것. 도구에 상관없는 일반 기능으로 쓴다.

7-7. 프로젝트 관리 — 임계경로(CPM) · 기능점수(FP) 🔥 🧮

임계경로 (Critical Path) 🧮

정의: 시작에서 종료까지의 경로 중 소요시간 합이 가장 긴 경로 = 프로젝트의 최소 완료 기간. 이 경로 위의 작업이 하루라도 늦어지면 전체 일정이 늦어진다(여유시간 0).

계산 절차
① 전진 계산: ES(가장 빠른 시작) = 선행 작업 EF 중 최댓값,  EF = ES + 소요시간
② 후진 계산: LF(가장 늦은 종료) = 후행 작업 LS 중 최솟값,  LS = LF − 소요시간
③ 여유시간(Slack) = LS − ES
④ Slack = 0 인 작업들을 이은 경로 = 임계경로

규칙
- 마일스톤(milestone) 노드는 소요시간 0, 합류 지점은 "가장 늦게 끝나는 선행 작업" 기준
- "전체 일정 지연 없이 작업 X를 가장 늦게 시작할 수 있는 날" = LS(X)

풀이 습관: 모든 경로를 나열해 합을 구하는 방법(작은 그래프)과 ES/LS 표(큰 그래프)를 둘 다 연습. 답안에는 경로 + 총 소요일을 같이 쓴다. △ PERT 3점 추정 = (낙관 + 4×보통 + 비관) / 6

기능점수 (Function Point) 🧮

정의: 사용자 관점의 기능 수와 복잡도로 소프트웨어 규모를 산정하는 방법. 언어와 무관하고 계획 단계(요구사항만 있을 때)에도 산정 가능 → LOC 방식의 한계를 보완.

구분 유형 의미
데이터 기능 ILF (내부논리파일) 애플리케이션 내부에서 유지·관리하는 데이터
EIF (외부인터페이스파일) 다른 애플리케이션이 관리하고 참조만 하는 데이터
트랜잭션(처리) 기능 EI (외부입력) 데이터를 입력·수정·삭제하는 처리
EO (외부출력) 계산·가공을 거쳐 내보내는 출력
EQ (외부조회) 가공 없이 조회만 하는 출력 
간이법: 복잡도를 따지지 않고 "평균 복잡도 가중치"를 일괄 적용
  FP = Σ (유형별 기능 개수 × 해당 가중치)

절차: ① 단위 업무별 표를 유형별로 세로 합산
      (EI는 입력·수정·삭제를 각각 1개 기능으로 셈)
      ② 유형 합계 × 가중치 ③ 전부 더함

⚠️ 함정: EI의 하위 칸(입력/수정/삭제)을 하나로 묶어 세지 말 것. 소수점 가중치가 있으면 마지막에 한 번만 반올림하거나 그대로 쓴다고 명시.

7-8. 최신 개발 트렌드 △

오픈소스 활용 주의사항은 7-5, 컨테이너 가상화는 1-10 참고.

개념 설명
DevOps 개발(Dev)과 운영(Ops)의 협업 문화 + 자동화. CI/CD 파이프라인으로 빌드-테스트-배포를 자동화
MSA (Microservice Architecture) 하나의 거대한 애플리케이션(모놀리식)을 독립 배포 가능한 작은 서비스 단위로 분리. 장점: 독립 배포·확장, 장애 격리 / 단점: 분산 시스템의 복잡도(서비스 간 통신, 데이터 일관성) 증가
함수형 프로그래밍 (Functional Programming) 상태 변경과 부수 효과(Side Effect)를 최소화하고, 순수 함수와 불변성(Immutability) 을 중심으로 코드를 작성하는 패러다임

구분내용예

도출 → 분석 → 명세 → 검증 (+ 전 과정에 걸친 요구 사항 관리)

단계활동기법
도출이해관계자에게서 요구를 수집인터뷰, 설문, 워크숍, 프로토타이핑, 관찰
분석충돌 해소, 우선순위, 범위 확정유스케이스, 자료 흐름도(DFD), 우선순위 기법(MoSCoW)
명세문서화요구 사항 명세서(SRS), 사용자 스토리
검증명세가 올바른지 확인검토(리뷰), 인스펙션, 워크스루, 인수 기준
  • 요구 사항 추적성: 요구 ↔ 설계 ↔ 코드 ↔ 테스트를 서로 연결해 두어, 변경 시 영향 범위를 알고 누락된 구현·테스트를 찾는다.
  • 검증(Verification): 제품을 올바르게 만들고 있는가(명세대로인가). 확인(Validation): 올바른 제품을 만들고 있는가(사용자 요구에 맞는가).

연관액터가 유스케이스를 사용실선
포함 (include)A 를 하려면 반드시 B 를 한다점선 화살표 A → B, «include»
확장 (extend)특정 조건에서만 B 가 A 에 추가된다점선 화살표 B → A, «extend»
일반화상위 액터·유스케이스를 구체화빈 삼각형 실선

화살표 방향이 헷갈리면: include 는 포함하는 쪽 → 포함되는 쪽, extend 는 확장하는 쪽 → 기본 유스케이스. (예: "주문하기" ─include→ "로그인", "쿠폰 적용" ─extend→ "주문하기")

클래스 다이어그램의 관계

관계의미표기코드
의존 (Dependency)잠깐 사용점선 화살표매개변수, 지역 변수
연관 (Association)계속 알고 있음실선필드로 참조
집합 (Aggregation)전체-부분, 부분이 독립적으로 존재빈 마름모 (전체 쪽)외부에서 주입받은 객체
합성 (Composition)전체-부분, 생명 주기를 같이함채운 마름모 (전체 쪽)내부에서 생성한 객체
일반화 (Generalization)상속 (is-a)빈 삼각형 실선extends
실체화 (Realization)인터페이스 구현빈 삼각형 점선implements
  • 결합 강도: 의존 < 연관 < 집합 < 합성 < 일반화
  • 집합 vs 합성 예: 학과-학생(학과가 없어져도 학생은 남음 → 집합), 주문-주문 항목(주문이 없어지면 항목도 사라짐 → 합성)

7-10. 소프트웨어 아키텍처 🔥

아키텍처는 나중에 바꾸기 어려운 결정들의 집합이다. 기능이 아니라 품질 속성(성능, 확장성, 가용성, 보안, 변경 용이성)이 구조를 결정하고, 품질 속성끼리는 서로 충돌한다(보안 ↔ 사용성, 성능 ↔ 변경 용이성).

아키텍처 스타일

스타일구조장점단점예
계층형 (Layered)표현 → 응용 → 도메인 → 데이터 접근. 위에서 아래로만 의존이해하기 쉬움, 역할 분리계층 통과 오버헤드, 변경이 여러 계층에 번짐전통적인 웹 애플리케이션
클라이언트-서버요청하는 쪽과 제공하는 쪽 분리중앙 관리서버가 병목·장애점웹, DB
파이프-필터데이터가 필터를 차례로 통과재사용·조합 쉬움상호작용에 부적합유닉스 파이프, 컴파일러, ETL
이벤트 기반생산자가 이벤트 발행, 소비자가 구독느슨한 결합, 확장 쉬움흐름 추적·순서 보장 어려움메시지 큐 기반 시스템
MVC모델 · 뷰 · 컨트롤러 분리화면과 로직 분리→ MVC 패턴웹 프레임워크
헥사고날 (포트와 어댑터)도메인이 중심, 외부(DB·UI·API)는 포트(인터페이스) 뒤의 어댑터외부 기술 교체·테스트 쉬움구조가 장황클린 아키텍처 계열
마이크로서비스업무 단위로 나눈 독립 배포 서비스아래 표아래 표대규모 서비스
  • 의존성 규칙(클린 아키텍처): 의존의 방향은 항상 바깥(프레임워크·DB) → 안쪽(도메인). 도메인은 DB 가 무엇인지 모른다. 이것을 가능하게 하는 것이 의존 역전 원칙(DIP) 이다.

예제. if (A && B) 에 대해 각 커버리지를 만족하는 최소 테스트 케이스는?

풀이
기준최소 케이스 (A, B)설명
결정(T,T), (F,T)전체 결과 참 1번, 거짓 1번
조건(T,F), (F,T)A·B 각각 참·거짓. 전체 결과는 둘 다 거짓 → 결정 커버리지는 불만족
조건/결정(T,T), (F,F)둘 다 만족
MC/DC(T,T), (F,T), (T,F)A 만 바꿔 결과가 바뀜 + B 만 바꿔 결과가 바뀜 → n+1 = 3개
다중 조건(T,T), (T,F), (F,T), (F,F)4개 전부

조건 커버리지를 만족해도 결정 커버리지를 만족하지 않을 수 있다는 점이 단골 함정이다.

커버리지 100% 는 "모든 코드가 실행되었다"는 뜻이지 "모든 동작이 검증되었다"는 뜻이 아니다. 검증문(assert)이 없는 테스트도 커버리지는 올린다.

3점 추정 (PERT)

기대 시간 = (낙관치 + 4 × 최빈치 + 비관치) / 6, 표준 편차 = (비관치 − 낙관치) / 6

예제. 낙관 4일, 최빈 7일, 비관 16일인 작업의 기대 시간과 표준 편차는?

풀이
  • 기대 시간 = (4 + 4×7 + 16) / 6 = 48 / 6 = 8일
  • 표준 편차 = (16 − 4) / 6 = 2일

법칙내용
브룩스의 법칙지연된 프로젝트에 인력을 더하면 더 늦어진다 (교육 비용 + 의사소통 경로 n(n−1)/2 증가)
파킨슨의 법칙일은 주어진 시간을 다 채울 때까지 늘어난다
파레토 법칙결함의 80% 는 20% 의 모듈에서 나온다
호프스태터의 법칙예상보다 항상 오래 걸린다, 이 법칙을 감안해도

위험 관리

식별 → 분석(발생 확률 × 영향도) → 대응 계획 → 감시

전가제3자에게 넘김보험, 외주 계약

스크럼

요소내용
역할제품 책임자(PO) — 무엇을 만들지와 우선순위 / 스크럼 마스터 — 장애물 제거, 프로세스 코칭 / 개발팀 — 자기 조직화
산출물제품 백로그, 스프린트 백로그, 증분(동작하는 제품)
이벤트스프린트(1~4주) / 스프린트 계획 / 일일 스크럼(15분) / 스프린트 리뷰(결과 시연) / 회고(일하는 방식 개선)
  • 번다운 차트: 남은 작업량을 날짜별로 그린 그래프. 이상선보다 위에 있으면 지연.
  • 완료의 정의(DoD): "끝났다"의 기준(코드 리뷰, 테스트 통과, 배포 가능)을 팀이 합의.

스크럼 vs 칸반

구분스크럼칸반
리듬고정 길이 스프린트연속 흐름
제한스프린트에 넣는 작업량진행 중 작업 수(WIP)
변경스프린트 중 범위 변경 지양언제든 우선순위 변경
역할PO, 스크럼 마스터정해진 역할 없음
지표속도 (Velocity)리드 타임, 사이클 타임
적합제품 개발운영, 유지보수, 요청 처리

XP (익스트림 프로그래밍) 실천법

짝 프로그래밍, 테스트 주도 개발, 지속적 통합, 리팩터링, 단순한 설계, 작은 릴리스, 코드 공동 소유, 코딩 표준, 고객 상주.

  • 5가지 가치: 의사소통, 단순성, 피드백, 용기, 존중

DevOps 로 이어지는 흐름

애자일이 "개발을 짧게 반복"했다면, DevOps 는 그 반복을 배포·운영까지 잇는다. 핵심 지표는 DORA 4대 지표 — 배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간. 구체적인 도구와 배포 전략은 → CI/CD · 배포 전략
