8-1. 트랜잭션 · 동시성 제어 🔥 🧮

등장 배경

계좌 이체는 "A에서 출금"과 "B에 입금" 두 연산이다. 출금만 되고 장애가 나면 돈이 사라진다. → 여러 연산을 하나로 묶어 "전부 반영하거나 전혀 반영하지 않는" 단위가 필요하다.

정의 🔥: 트랜잭션(Transaction)은 데이터베이스의 상태를 변화시키는 하나의 논리적 작업 단위로, 한꺼번에 모두 수행되어야 하는 일련의 연산 묶음이다.

↗ 요약 페이지 · ACID

TCL과 상태 전이 ⭐

명령어 기능
COMMIT 변경 내용을 DB에 영구 반영하고 트랜잭션 종료
ROLLBACK 변경 내용을 취소하고 트랜잭션 시작 전 상태로 복귀
SAVEPOINT 중간 저장점 지정 → 그 지점까지만 부분 ROLLBACK 가능 
            ┌──────────► 부분 완료 ──COMMIT──► 완료(Committed)
 활동(Active)               (Partially Committed)
            └──오류──► 실패(Failed) ──ROLLBACK──► 철회(Aborted)

동시성 제어를 하지 않을 때의 문제 🔥 🧮

문제 상황
갱신 손실 (Lost Update) 두 트랜잭션이 같은 값을 읽고 각자 갱신 → 나중에 쓴 값이 앞의 갱신을 덮어씀
오손 읽기 (Dirty Read) 커밋되지 않은 데이터를 읽었는데 그 트랜잭션이 롤백됨
반복 불가능 읽기 (Non-Repeatable Read) 같은 행을 두 번 읽었는데 그 사이 다른 트랜잭션이 수정해 값이 다름
팬텀 읽기 (Phantom Read) 같은 조건 조회인데 그 사이 삽입·삭제로 행 개수가 달라짐
연쇄 복귀 (Cascading Rollback) 롤백된 트랜잭션의 값을 읽은 다른 트랜잭션까지 줄줄이 롤백

타임라인 추적 (초기 잔고 10,000, T1 +10,000, T2 +20,000)

시간 │ T1 (+10,000)              │ T2 (+20,000)              │ A (DB)
─────┼───────────────────────────┼───────────────────────────┼───────
 t1  │ Read(A) → 10,000          │                           │ 10,000
 t2  │                           │ Read(A) → 10,000          │ 10,000
 t3  │ Write(A) ← 20,000         │                           │ 20,000
 t4  │                           │ Write(A) ← 30,000         │ 30,000  ← T1의 갱신 소실
정상 결과는 40,000 → 갱신 손실(Lost Update)

해결: 동시성 제어 기법 🔥

로킹(Locking) — 데이터 항목에 잠금을 걸고 COMMIT/ROLLBACK 때까지 유지

요청 \ 보유 공유 락(S, 읽기) 배타 락(X, 쓰기)
S 요청 ✅ 호환 ❌ 대기
X 요청 ❌ 대기 ❌ 대기

2단계 로킹 규약 (2PL, Two-Phase Locking Protocol) 🔥

 락 개수
   ▲        ╱‾‾‾‾╲
   │      ╱        ╲
   │    ╱  확장      ╲  축소
   │  ╱  (Growing)    ╲ (Shrinking)
   └──────────────────────────► 시간
        lock만 획득 │ unlock만 수행
                 Lock Point
  • 확장 단계(Growing): lock 획득만 가능, unlock 불가 / 축소 단계(Shrinking): unlock만 가능, 새 lock 불가
  • 장점: 모든 트랜잭션이 2PL을 지키면 직렬 가능성(Serializability) 보장 — 병행 실행 결과가 어떤 직렬 실행 결과와 같다
  • 단점: 교착상태 발생 가능(서로의 lock을 기다림), 연쇄 복귀 가능 → Strict 2PL(X-lock을 커밋까지 유지)·Rigorous 2PL로 보완

기타 기법: 타임스탬프 순서(Timestamp Ordering), 낙관적 검증(Optimistic/Validation — 충돌이 드물다고 보고 커밋 시점에 검사), MVCC(다중 버전 — 읽기는 이전 버전을 봐서 잠금 대기 없음), 실무 SELECT … FOR UPDATE, 비관적 락 vs 낙관적 락(version 컬럼)

DB 교착상태 예방 🔥

  • 4조건(상호배제·점유와 대기·비선점·환형 대기) 중 하나를 깨뜨린다 (1-6 Deadlock과 같은 원리)
  • 필요한 lock을 시작 시 한꺼번에 획득 → 점유와 대기 제거
  • 데이터 항목에 순서를 매겨 순서대로만 lock → 환형 대기 제거
  • 타임스탬프 기반 기법 (오래된 = 타임스탬프가 작은 트랜잭션)
기법 오래된 T가 젊은 T의 lock을 요청 젊은 T가 오래된 T의 lock을 요청
Wait-Die (비선점) 오래된 T가 기다림 젊은 T가 죽음(롤백)
Wound-Wait (선점) 오래된 T가 젊은 T를 롤백시킴(Wound) 젊은 T가 기다림
  • 예방이 아닌 탐지·회복: Wait-for 그래프에서 사이클 탐지 → 희생자 선택 후 롤백

격리 수준 (Isolation Level) ⭐

격리 수준 Dirty Read Non-Repeatable Phantom
Read Uncommitted 발생 발생 발생
Read Committed 방지 발생 발생
Repeatable Read 방지 방지 발생
Serializable 방지 방지 방지

격리 수준이 높을수록 일관성↑, 동시성(성능)↓.

OS 동기화 ↔ DB 동시성 제어 대응표 🔥

OS (Part 1-5) DB
실행 주체 스레드/프로세스 트랜잭션
문제 이름 경쟁 상태(Race Condition) 갱신 손실 등 이상 현상
해결 도구 뮤텍스·세마포어 (개발자가 코드에 작성) 로킹·2PL·격리 수준 (DBMS가 관리)

2PL 변형과 동시성 서술 4단 템플릿 🔥 ✍️

변형 특징 효과
기본 2PL 확장(lock만) → 축소(unlock만) 직렬 가능성 (교착은 못 막음)
보수적 2PL 시작 전 필요한 lock 일괄 획득 교착 없음
엄격 2PL X-lock을 COMMIT까지 유지 연쇄 복귀 방지
강엄격 2PL 모든 lock을 COMMIT까지 가장 안전

동시성 서술 4단 템플릿 (계좌 동시 이체 유형)

  1. 현상 이름: 갱신 손실(Lost Update)
  2. 타임라인: T1·T2가 같은 잔액을 읽고 각자 갱신 → 한쪽 결과가 덮어써짐
  3. 결과: 잔액 불일치, 무결성 위반
  4. 해결: X-Lock을 COMMIT까지 유지 + 2PL, SELECT … FOR UPDATE, 격리 수준 SERIALIZABLE, 낙관적 동시성(version 컬럼), 출금+입금을 한 트랜잭션으로(원자성), 교착 대비(타임아웃·Wait-Die)

8-2. SQL 🔥 ✍️

아래 예시는 설명용 스키마다. 다른 스키마(영업지점/직원/판매실적, 직원/부서/급여, 부서/직원/요청)로도 같은 문법을 직접 작성해 볼 것.

학과(학과코드, 학과명) / 학생(학번, 이름, 학과코드*, 입학일자) / 수강(학번*, 과목코드, 점수, 수강년월) — 밑줄 대신 앞쪽이 기본키, * 는 외래키

분류 명령어 용도
DDL (정의) CREATE, ALTER, DROP, TRUNCATE 테이블·뷰·인덱스 구조 정의
DML (조작) SELECT, INSERT, UPDATE, DELETE 데이터 조회·변경
DCL (제어) GRANT, REVOKE 권한 부여·회수
TCL (트랜잭션) COMMIT, ROLLBACK, SAVEPOINT 트랜잭션 제어 (8-1)

SELECT — 조건 · 정렬 · 조인 🔥

-- 조건 + 정렬
SELECT 학번, 점수
FROM 수강
WHERE 점수 >= 90 AND 수강년월 = '202403'
ORDER BY 학번 ASC;              -- DESC = 내림차순

-- 조인: 다른 테이블의 조건으로 찾기
SELECT S.학번, S.이름
FROM 학생 S, 학과 D             -- 또는 학생 S JOIN 학과 D ON S.학과코드 = D.학과코드
WHERE S.학과코드 = D.학과코드
  AND D.학과명 = '컴퓨터공학과'
ORDER BY S.입학일자 DESC;

-- 서브쿼리로 같은 결과
SELECT 학번 FROM 학생
WHERE 학과코드 IN (SELECT 학과코드 FROM 학과 WHERE 학과명 = '컴퓨터공학과');

⚠️ 함정: ① 조인 조건(S.학과코드 = D.학과코드)을 빠뜨리면 카티션 곱 ② 같은 이름의 열은 테이블 별칭으로 구분 ③ 'YYYYMMDD' 문자열 날짜는 사전순 = 날짜순이라 문자열 비교 가능, 기간은 BETWEEN '20240101' AND '20241231' 또는 LIKE '2024%' ④ 숫자를 VARCHAR로 저장했으면 비교 방식에 주의(필요하면 CAST)

집계 · GROUP BY · HAVING 🔥

-- 학과별 학생 수, 2명 이상인 학과만
SELECT D.학과명, COUNT(*) AS 학생수
FROM 학생 S JOIN 학과 D ON S.학과코드 = D.학과코드
GROUP BY D.학과명
HAVING COUNT(*) >= 2;

-- 특정 학과 학생들의 2024년 점수 합계
SELECT SUM(C.점수) AS 총점
FROM 수강 C JOIN 학생 S ON C.학번 = S.학번
           JOIN 학과 D ON S.학과코드 = D.학과코드
WHERE D.학과명 = '경영학과' AND C.수강년월 LIKE '2024%';

실행 순서:  FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
WHERE HAVING
거르는 대상 개별 행 (그룹화 전) 그룹 (그룹화 후)
집계 함수 사용 불가 가능 (COUNT(*) >= 2)

⚠️ 함정: GROUP BY를 쓰면 SELECT에는 그룹 기준 열 + 집계 함수만 올 수 있다. "~별"이 보이면 GROUP BY, "~인 그룹만"이면 HAVING.

INSERT · UPDATE · DELETE 🔥

INSERT INTO 학과 (학과코드, 학과명) VALUES ('D04', '통계학과');

UPDATE 수강
SET 점수 = 점수 * 1.1                       -- 10% 증가
WHERE 수강년월 = '202312'
  AND 학번 IN (SELECT 학번 FROM 학생
               WHERE 입학일자 <= '20231231'
                 AND (졸업일자 IS NULL OR 졸업일자 >= '20231231'));

DELETE FROM 학과 WHERE 학과명 LIKE '경%';   -- '경'으로 시작

⚠️ 함정: NULL 비교는 반드시 IS NULL / IS NOT NULL (= NULL은 항상 거짓). LIKE 패턴: % = 0개 이상 임의 문자, _ = 정확히 1문자.

무결성 제약과 참조 무결성 오류 🔥

무결성 내용
개체 무결성 기본키는 NULL 불가·중복 불가
참조 무결성 외래키 값은 참조하는 테이블의 기본키에 존재하는 값이거나 NULL
도메인 무결성 속성 값이 정의된 도메인(타입·범위)에 속함

참조 중인 부모 행을 DELETE하면 오류가 나는 이유: 자식 테이블(학생.학과코드)이 그 값을 외래키로 참조하고 있는데 부모(학과)의 행을 지우면, 자식의 외래키가 존재하지 않는 값을 가리키게 되어 참조 무결성 위반 → 기본 옵션(RESTRICT/NO ACTION)이 삭제를 거부한다.

외래키 옵션 부모 행 삭제 시
RESTRICT / NO ACTION 삭제 거부 (기본)
CASCADE 참조하는 자식 행도 함께 삭제
SET NULL 자식의 외래키를 NULL로
SET DEFAULT 자식의 외래키를 기본값으로

DDL · VIEW 🔥

ALTER TABLE 학과 ADD 위치 CHAR(8);          -- 열 추가
ALTER TABLE 학과 MODIFY 위치 VARCHAR(20);   -- 타입 변경 (DBMS마다 ALTER COLUMN)
ALTER TABLE 학과 DROP COLUMN 위치;

CREATE VIEW 재학생 AS                        -- 뷰 = 가상 테이블
SELECT 학번, 이름, 학과코드
FROM 학생
WHERE 입학일자 >= '20200101'
WITH CHECK OPTION;                          -- 뷰 조건을 벗어나는 변경 금지
DELETE vs TRUNCATE vs DROP ⭐ DELETE TRUNCATE DROP
분류 DML DDL DDL
대상 조건에 맞는 행 모든 행 (구조 유지) 테이블 자체
ROLLBACK 가능 불가(대부분) 불가

뷰의 장점: 열·행을 제한해 보안(필요한 데이터만 노출), 복잡한 조인을 숨겨 사용 단순화, 논리적 독립성. 단점: 뷰는 인덱스를 가질 수 없고 조인 뷰 등은 갱신 제약.

DCL — GRANT · REVOKE 🔥

GRANT INSERT ON 학생 TO User1 WITH GRANT OPTION;   -- 권한 + 남에게 다시 부여할 권한
GRANT SELECT ON 학생 TO User2;                     -- 권한만

REVOKE INSERT ON 학생 FROM User1 RESTRICT;  -- User1이 남에게 준 권한이 있으면 취소 거부
REVOKE INSERT ON 학생 FROM User1 CASCADE;   -- User1이 남에게 준 권한까지 연쇄 취소
REVOKE GRANT OPTION FOR INSERT ON 학생 FROM User1;  -- 권한은 두고 "부여할 권한"만 취소

⚠️ 함정: "권한 전달 허용" = WITH GRANT OPTION, "연쇄 취소 허용/불허" = CASCADE/RESTRICT. 전달 권한이 없는 사용자에게는 연쇄 취소 여부가 "해당 사항 없음"이다.

별칭에 작은따옴표 큰따옴표 "총급여" 또는 공백 없는 이름
NULL 기간 조건 (퇴사일자 IS NULL OR 퇴사일자 >= 'X') 또는 NVL(퇴사일자,'99999999') >= 'X'
WHERE 뒤에 JOIN FROM … JOIN … ON → WHERE 순서
  • 뷰 조건: "속성 중 ~만" = SELECT 절, "튜플 중 ~만" = WHERE 절.

8-3. 이상 현상 · 정규화 🔥 ✍️

↗ 요약 페이지 · Anomaly (이상 현상)

↗ 요약 페이지 · 정규화 — 1NF부터 6NF까지

함수 종속 다이어그램 → 2NF · 3NF 분해 그리기 🔥 ✍️

예) 수강지도(학번, 과목번호, 지도교수, 학과, 성적)   기본키 = (학번, 과목번호)
    함수 종속: (학번, 과목번호) → 성적
               학번 → 지도교수,  학번 → 학과,  지도교수 → 학과

① 2NF (부분 함수 종속 제거): 기본키 일부(학번)에만 종속된 속성을 분리
     수강(학번, 과목번호, 성적)          ← 기본키에 밑줄
     지도(학번, 지도교수, 학과)

② 3NF (이행적 함수 종속 제거): 학번 → 지도교수 → 학과
     지도(학번, 지도교수)
     교수소속(지도교수, 학과)
  • 답안에는 각 릴레이션의 기본키에 밑줄을 반드시 표시
  • 함수 종속을 물으면 "X → Y" 형태로 모두 나열한 뒤, 어떤 것이 부분/이행 종속인지 이름을 붙인다
  • 이상 현상은 삽입·삭제·갱신 각각을 그 릴레이션의 구체적 예시로 서술 (위 Anomaly 표 형식)

8-4. 회복 · 트리거 ⭐

🔥 Recovery — Redo vs Undo

로그(Log) 기반 회복 기법의 두 축:

Redo (재실행) Undo (취소)
적용 대상 커밋된(Commit) 트랜잭션 중, 그 결과가 디스크에 아직 반영 안 된 경우 커밋되지 않은(미완료) 트랜잭션이 장애 시점에 디스크에는 이미 일부 반영된 경우
복원 방식 로그에 기록된 변경 후 값(After Image) 을 이용해 다시 한번 그 연산을 재수행 로그에 기록된 변경 전 값(Before Image) 을 이용해 원래 상태로 되돌림
목적 커밋된 작업이 디스크에 확실히 반영되게 함(지속성 보장) 완료되지 않은 작업의 흔적을 모두 제거하여 원자성 보장

판단 기준: 로그에 <Ti, START>와 <Ti, COMMIT>이 모두 있으면 Redo, <Ti, COMMIT>이 없으면 Undo 대상이다.

🔥 Trigger (트리거) 사용 시 주의사항

정의: INSERT, UPDATE, DELETE 같은 특정 이벤트가 발생할 때 자동으로 실행되는 데이터베이스 내부 동작(프로시저).

주의사항 2가지 1. 연쇄 실행(Trigger Chaining)으로 인한 예측 불가능성: 트리거가 실행한 DML이 또 다른 트리거를 발동시켜, 개발자가 의도하지 않은 연쇄적·재귀적 실행이 일어날 수 있다. 이는 디버깅을 어렵게 하고, 심하면 무한 루프로 이어질 수 있다. 2. 성능 저하 및 숨겨진 로직: 트리거는 애플리케이션 코드에 드러나지 않고 DB 내부에 숨겨져 실행되므로, 데이터 변경마다 자동으로 추가 연산이 수행되어 대량 데이터 처리 시 성능이 저하될 수 있고, 다른 개발자가 애플리케이션 코드만 보고는 트리거의 존재와 부수 효과를 알기 어려워 유지보수성이 떨어진다.

(추가 가능 사항: 트랜잭션 범위 내에서 실행되므로 트리거 오류가 전체 트랜잭션을 롤백시킬 수 있음, 과도한 트리거 사용은 비즈니스 로직이 DB와 애플리케이션에 분산되어 일관성 관리가 어려워짐)

  • 클러스터드 인덱스(데이터 자체가 키 순서로 정렬, 테이블당 1개) vs 논클러스터드(별도 구조).

반정규화

정규화는 중복을 없애 이상 현상을 막지만 조인이 늘어 조회가 느려진다. 조회 성능을 위해 의도적으로 중복을 허용하는 것이 반정규화다.

기법내용대가
중복 컬럼 추가조인으로 가져오던 값을 복사해 둠원본 변경 시 함께 갱신
파생 컬럼 추가합계·건수를 미리 계산해 저장갱신 비용, 불일치 위험
테이블 병합1:1, 1:N 테이블을 합침중복, NULL 증가
테이블 분할자주 쓰는 컬럼·행만 분리 (수직/수평)전체 조회 시 조인·UNION
요약 테이블통계를 별도 테이블로실시간성 저하

순서는 항상 정규화 먼저, 측정 후 필요한 곳만 반정규화. 반정규화는 데이터 무결성을 애플리케이션이 책임지게 만든다.

8-7. 관계 대수 ⭐ 🧮

관계 대수는 원하는 결과를 얻는 절차를 기술한다(절차적). 관계 해석은 원하는 결과가 무엇인지를 기술한다(비절차적). SQL 은 관계 해석에 가깝고, DBMS 내부의 실행 계획은 관계 대수 연산의 트리다.

교집합R ∩ S둘 다에 있는 튜플INTERSECT

  • 순수 관계 연산: 셀렉션, 프로젝션, 조인, 디비전 / 일반 집합 연산: 합집합, 교집합, 차집합, 카티션 곱
  • 합집합·교집합·차집합은 두 릴레이션의 차수(열 수)와 도메인이 같아야 한다(합병 가능).

예제. R 의 차수 3, 카디널리티 4. S 의 차수 2, 카디널리티 5. R × S 의 차수와 카디널리티는? 그리고 "컴퓨터공학과 학생의 이름"을 관계 대수로 쓰면?

풀이
  • 카티션 곱의 차수는 합: 3 + 2 = 5
  • 카티션 곱의 카디널리티는 곱: 4 × 5 = 20
  • π 이름 (σ 학과='컴퓨터공학' (학생))
  • 셀렉션을 먼저 해 행을 줄인 뒤 조인·프로젝션을 하는 것이 효율적이다. 옵티마이저가 하는 조건 밀어 넣기(predicate pushdown) 가 이것이다.

복합 인덱스와 선두 컬럼

인덱스 (a, b, c) 는 a 로 정렬하고, a 가 같으면 b, b 가 같으면 c 로 정렬한 구조다.

조건인덱스 사용
a = ?✅
a = ? AND b = ?✅
a = ? AND b = ? AND c = ?✅
b = ?❌ (선두 컬럼 없음)
a = ? AND c = ?a 까지만 탐색에 사용, c 는 걸러내기
a > ? AND b = ?a 범위까지만 탐색에 사용 (범위 조건 뒤 컬럼은 탐색에 못 씀)
  • 컬럼 순서 원칙: 동등 조건 컬럼 → 범위 조건 컬럼, 그리고 선택도가 좋은(값 종류가 많은) 컬럼을 앞에.
  • 커버링 인덱스: 쿼리에 필요한 모든 컬럼이 인덱스에 있어 테이블에 가지 않고 인덱스만으로 답하는 것.

  • rows(예상 검사 행 수)가 결과 건수에 비해 지나치게 크면 인덱스가 맞지 않는 것이다.

  • 옵티마이저는 통계 정보로 비용을 추정한다. 통계가 낡으면 잘못된 계획을 고른다.

8-9. SQL 심화 — 실행 순서 · 서브쿼리 · 윈도 함수 🔥 ✍️

논리적 실행 순서

FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

  • WHERE 에서 SELECT 의 별칭을 쓸 수 없는 이유, WHERE 에 집계 함수를 쓸 수 없는 이유가 이 순서다.
  • WHERE 는 그룹화 전 행을 거르고, HAVING 은 그룹화 후 그룹을 거른다.

NULL 과 3값 논리

NULL 은 "값을 모른다"이다. 비교 결과는 참·거짓이 아니라 UNKNOWN 이고, WHERE 는 참인 행만 통과시킨다.

식결과
NULL = NULLUNKNOWN → IS NULL 을 써야 한다
NULL + 1NULL
COUNT(*) vs COUNT(col)전체 행 수 vs NULL 이 아닌 행 수
AVG(col), SUM(col)NULL 을 빼고 계산
x NOT IN (1, NULL)항상 UNKNOWN → 결과 0건 (단골 함정)
  • NOT IN 의 서브쿼리에 NULL 이 섞일 수 있으면 NOT EXISTS 를 쓴다.
  • NULL 대체: COALESCE(col, 0)

종류위치특징

SELECT c.name FROM customer c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- CTE: 서브쿼리에 이름을 붙여 읽기 쉽게
WITH monthly AS (
    SELECT customer_id, SUM(amount) AS total
    FROM orders
    WHERE order_date >= '2025-01-01'
    GROUP BY customer_id
)
SELECT c.name, m.total
FROM customer c JOIN monthly m ON m.customer_id = c.id
WHERE m.total >= 1000000;

-- 재귀 CTE: 조직도·카테고리 같은 계층 구조
WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 1 AS depth FROM employee WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1
    FROM employee e JOIN org o ON e.manager_id = o.id
)
SELECT * FROM org;

윈도 함수

GROUP BY 는 행을 합쳐 그룹당 한 행으로 만든다. 윈도 함수는 행을 그대로 둔 채 각 행에 그룹 기준 계산 결과를 붙인다.

SELECT dept, name, salary,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
       SUM(salary)  OVER (PARTITION BY dept)                      AS dept_total,
       SUM(salary)  OVER (ORDER BY hire_date)                     AS running_total,
       LAG(salary)  OVER (PARTITION BY dept ORDER BY hire_date)   AS prev_salary
FROM employee;
함수점수 100, 90, 90, 80 일 때설명
ROW_NUMBER()1, 2, 3, 4동점이어도 다른 번호
RANK()1, 2, 2, 4동점은 같은 순위, 다음 순위를 건너뜀
DENSE_RANK()1, 2, 2, 3동점은 같은 순위, 건너뛰지 않음
LAG / LEAD—이전 / 다음 행의 값
SUM() OVER (ORDER BY …)—누적 합
NTILE(n)—n 개 구간으로 나눔

예제. 부서별 급여 상위 2명을 구하라.

풀이 
SELECT dept, name, salary
FROM (
    SELECT dept, name, salary,
           DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
    FROM employee
) t
WHERE rnk <= 2;

윈도 함수는 SELECT 단계에서 계산되므로 같은 쿼리의 WHERE 에서 바로 쓸 수 없다. 한 번 감싸야 한다. 동점자를 모두 포함하려면 DENSE_RANK, 정확히 2명만이면 ROW_NUMBER 를 쓴다.

락의 종류

구분종류설명

모드배타 락 (X)쓰기. 어떤 락과도 공존 불가
범위테이블 / 페이지 / 행 락범위가 좁을수록 동시성↑, 관리 비용↑
InnoDB레코드 락인덱스 레코드 하나
InnoDB갭 락레코드 사이의 틈 → 그 범위의 삽입을 막음
InnoDB넥스트 키 락레코드 락 + 갭 락 → 팬텀 리드 방지
  • InnoDB 의 행 락은 인덱스에 건다. 조건에 맞는 인덱스가 없으면 훑은 모든 행에 락이 걸려 사실상 테이블 락처럼 동작한다.

MVCC (다중 버전 동시성 제어)

"읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다."

  • 행을 고칠 때 이전 버전을 언두 로그에 남긴다.
  • 읽는 트랜잭션은 자신의 스냅샷 시점에 커밋되어 있던 버전을 본다(일관된 읽기). 락을 걸지 않는다.
  • 격리 수준별 스냅샷 시점: READ COMMITTED 는 문장마다 새 스냅샷, REPEATABLE READ 는 트랜잭션의 첫 읽기 시점 스냅샷을 유지.
  • 대가: 오래 열린 트랜잭션이 있으면 그 시점 이후의 옛 버전을 지우지 못해 언두 로그가 커진다(PostgreSQL 에서는 죽은 튜플 → VACUUM).

격리 수준과 이상 현상의 정의는 → 격리 수준

낙관적 락 vs 비관적 락

구분비관적 락낙관적 락
가정충돌이 자주 난다충돌이 드물다
방법읽을 때 미리 잠금 SELECT … FOR UPDATE잠그지 않고, 갱신 시 버전 비교
충돌 시대기갱신 실패 → 재시도 또는 오류
장점충돌이 많아도 정합성 확실락 대기 없음, 처리량 높음
단점대기·교착 가능, 처리량 저하충돌이 잦으면 재시도 폭증
-- 낙관적 락: 버전이 그대로일 때만 갱신
UPDATE product
SET stock = stock - 1, version = version + 1
WHERE id = 10 AND version = 7;
-- 영향받은 행이 0 이면 다른 트랜잭션이 먼저 고친 것 → 재시도

-- 원자적 갱신: 읽고-계산하고-쓰는 대신 한 문장으로
UPDATE product SET stock = stock - 1 WHERE id = 10 AND stock >= 1;
  • 갱신 손실(Lost Update): 두 트랜잭션이 같은 값을 읽고 각자 계산해 쓰면 하나가 덮어쓰인다. 위의 세 가지(비관적 락, 낙관적 락, 원자적 갱신) 중 하나로 막는다.

DB 교착 상태 대응

  • DBMS 는 대기 그래프에서 사이클을 탐지해 한 트랜잭션을 희생자로 골라 롤백한다. 애플리케이션은 이 오류를 받아 재시도해야 한다.
  • 예방: 여러 행·테이블을 항상 같은 순서로 잠근다. 트랜잭션을 짧게. 적절한 인덱스로 락 범위를 좁힌다.

CAP 정리

분산 시스템은 일관성(C), 가용성(A), 분할 내성(P) 셋을 동시에 만족할 수 없다. 네트워크 분할은 피할 수 없으므로 실제 선택은 분할이 났을 때 C 와 A 중 무엇을 지킬 것인가다.

선택분할 시 동작예
CP일관성을 지키려고 일부 요청을 거절금융 원장, ZooKeeper, etcd, HBase
AP응답은 하되 오래된 값일 수 있음Cassandra, DynamoDB(기본), DNS
  • PACELC: 분할(P)이 나면 A 와 C 사이에서, 평상시(E)에도 지연(L)과 일관성(C) 사이에서 선택해야 한다.
  • CAP 의 C(모든 노드가 같은 값을 보임)는 ACID 의 C(무결성 제약 유지)와 다른 개념이다.
