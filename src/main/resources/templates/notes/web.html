11-1. 웹 아키텍처 기본 🔥

웹 서버 vs WAS

구분웹 서버WAS (웹 애플리케이션 서버)
역할정적 콘텐츠 제공, 요청 전달동적 콘텐츠 생성 (비즈니스 로직, DB 연동)
예Nginx, Apache HTTP ServerTomcat, Jetty, Undertow
추가 기능리버스 프록시, 로드 밸런싱, TLS 종료, 압축, 캐싱서블릿 컨테이너, 스레드 풀, 커넥션 풀

둘을 분리하는 이유: 정적 요청을 WAS 까지 보내지 않아 부하 감소 / WAS 를 여러 대로 늘리고 앞에서 분산 / WAS 를 외부에 직접 노출하지 않음(보안) / WAS 를 하나씩 내렸다 올려 무중단 배포.

3계층 구조

[프레젠테이션 계층]      [애플리케이션 계층]          [데이터 계층]
 브라우저 / 앱   ──▶   웹 서버 ──▶ WAS      ──▶   DB, 캐시, 저장소
  • 계층을 나누면 각 계층을 독립적으로 확장·교체할 수 있다. 일반적으로 애플리케이션 계층은 무상태로 만들어 수평 확장하고, 상태는 데이터 계층에 모은다.

CSR vs SSR

구분CSR (클라이언트 사이드 렌더링)SSR (서버 사이드 렌더링)
HTML 생성브라우저가 JS 로 그림서버가 완성된 HTML 을 보냄
첫 화면느림 (JS 를 받아 실행해야 보임)빠름
이후 화면 전환빠름 (필요한 데이터만 요청)페이지마다 서버 왕복
검색 엔진 최적화불리유리
서버 부하작음큼
예React, Vue 로 만든 SPAJSP, Thymeleaf, Next.js(SSR 모드)
  • SPA: 페이지 하나를 받은 뒤 화면 전환을 JS 가 처리. MPA: 화면마다 새 HTML 을 요청.
  • SSG: 빌드 시점에 HTML 을 미리 만들어 둠(블로그, 문서). 하이드레이션: 서버가 보낸 HTML 에 브라우저에서 JS 이벤트를 연결하는 과정.

동일 출처 정책과 CORS

  • 출처(Origin) = 스킴 + 호스트 + 포트. 셋 중 하나라도 다르면 다른 출처다.
  • 동일 출처 정책(SOP): 브라우저는 스크립트가 다른 출처의 응답을 읽는 것을 막는다. 악성 사이트가 로그인된 은행 사이트의 데이터를 읽어 가는 것을 막기 위함이다.
  • CORS: 서버가 응답 헤더로 "이 출처에는 허용한다"고 알려 SOP 를 선택적으로 완화하는 규약.
[사전 요청]  OPTIONS /api/orders
             Origin: https://shop.example.com
             Access-Control-Request-Method: PUT
[사전 응답]  Access-Control-Allow-Origin: https://shop.example.com
             Access-Control-Allow-Methods: GET, PUT
             Access-Control-Allow-Credentials: true
[본 요청]    PUT /api/orders/1
요청 종류조건동작
단순 요청GET·HEAD·POST + 기본 헤더·콘텐츠 타입바로 보내고 응답 헤더로 판단
사전 요청 (Preflight)그 외 (PUT, DELETE, JSON 본문, 사용자 정의 헤더)OPTIONS 로 먼저 허용 여부 확인
  • CORS 는 브라우저가 강제하는 규칙이다. 서버 간 호출이나 curl 에는 적용되지 않는다. 따라서 CORS 는 접근 통제 수단이 아니다.
  • 쿠키를 함께 보내려면 Allow-Credentials: true 이고 Allow-Origin 에 * 를 쓸 수 없다.

실무 체크리스트

  • 오류 응답 형식 통일: 상태 코드 + 기계가 읽을 오류 코드 + 사람이 읽을 메시지 + 추적 ID.
  • 버전 관리: /v1/orders 또는 헤더. 기존 클라이언트를 깨는 변경(필드 삭제, 의미 변경)만 버전을 올린다.
  • 페이징: 오프셋 방식은 뒤로 갈수록 느리고 중간 삽입 시 중복·누락 → 대량 데이터는 커서(키셋) 방식.
  • 멱등 키: 결제 같은 POST 에 클라이언트가 고유 키를 보내고, 서버는 같은 키의 재요청에 저장해 둔 결과를 돌려준다.
  • 내부 구조 은닉: 엔티티를 그대로 반환하지 않고 DTO 로 변환한다.

OAuth 2.0

사용자의 패스워드를 제3자 앱에 주지 않고, 제한된 권한만 위임하는 인가 프레임워크.

역할예 ("구글 캘린더 연동")
자원 소유자사용자
클라이언트연동하려는 앱
인가 서버구글 로그인·동의 화면
자원 서버구글 캘린더 API

인가 코드 승인 방식 (Authorization Code Grant)

1. 앱 → 사용자를 인가 서버로 리다이렉트 (client_id, redirect_uri, scope, state)
2. 사용자 → 인가 서버에서 로그인하고 권한에 동의
3. 인가 서버 → redirect_uri 로 인가 코드 전달 (브라우저 경유)
4. 앱 서버 → 인가 코드 + client_secret 으로 토큰 요청 (서버 간 직접 통신)
5. 인가 서버 → 액세스 토큰 (+ 리프레시 토큰) 발급
6. 앱 서버 → 액세스 토큰으로 자원 서버 API 호출
  • 코드를 거치는 이유: 토큰이 브라우저 주소창·기록에 노출되지 않게 하려고. 코드는 일회용이고 수명이 짧으며, 교환할 때 클라이언트 인증이 필요하다.
  • state: 요청과 응답을 묶는 임의 값 → CSRF 방지.
  • PKCE: 비밀을 안전하게 보관할 수 없는 앱(모바일, SPA)을 위해, 요청 시 만든 검증 값의 해시를 보내고 교환 시 원본을 제시한다. 가로챈 코드만으로는 토큰을 받을 수 없다.
  • OpenID Connect (OIDC): OAuth 2.0 위에 인증 계층을 더한 것. 사용자 정보를 담은 ID 토큰(JWT) 을 추가로 준다. "구글로 로그인"이 이것이다.

클라이언트 자격 증명사용자 없이 서버 간 호출

11-4. Spring 핵심 — IoC · DI · AOP 🔥

IoC 와 DI

  • 제어의 역전(IoC): 객체의 생성과 연결을 개발자 코드가 아니라 컨테이너가 맡는다.
  • 의존성 주입(DI): 객체가 필요로 하는 의존 객체를 스스로 만들지 않고 밖에서 넣어 받는다.
// DI 없음: 구현 클래스에 직접 의존 → 교체·테스트가 어렵다
public class OrderService {
    private final PaymentClient client = new KakaoPaymentClient();
}

// DI: 인터페이스에 의존하고 구현은 컨테이너가 주입
@Service
public class OrderService {
    private final PaymentClient client;

    public OrderService(PaymentClient client) {   // 생성자 주입
        this.client = client;
    }
}
주입 방식특징
생성자 주입 (권장)final 로 불변 보장, 의존성 누락 시 생성 자체가 안 됨, 순환 참조를 기동 시점에 발견, 컨테이너 없이 테스트 가능
세터 주입선택적 의존성, 변경 가능
필드 주입 (@Autowired)간결하지만 불변 불가, 테스트 시 주입이 어려움, 의존성이 숨음

빈 (Bean)

컨테이너(ApplicationContext)가 생성·관리하는 객체.

등록 방법설명
컴포넌트 스캔@Component 와 그 특수화 @Service, @Repository, @Controller 가 붙은 클래스를 자동 등록

  • @Configuration 클래스는 CGLIB 프록시로 감싸져, @Bean 메서드를 여러 번 호출해도 같은 싱글턴을 돌려준다.
  • 같은 타입의 빈이 여러 개면 @Primary 나 @Qualifier 로 고른다.

AOP (관점 지향 프로그래밍)

로깅, 트랜잭션, 보안, 성능 측정처럼 여러 곳에 흩어지는 횡단 관심사를 핵심 로직에서 분리한다.

용어뜻
애스펙트 (Aspect)횡단 관심사를 모듈화한 것 (어드바이스 + 포인트컷)
어드바이스 (Advice)무엇을 할 것인가 — @Before, @After, @AfterReturning, @AfterThrowing, @Around
조인 포인트 (Join Point)어드바이스가 끼어들 수 있는 지점 (Spring AOP 는 메서드 실행)
포인트컷 (Pointcut)어디에 적용할지 고르는 표현식
위빙 (Weaving)애스펙트를 대상에 적용하는 과정 (Spring 은 런타임 프록시)
@Aspect
@Component
public class TimingAspect {
    @Around("execution(* com.example..service.*.*(..))")
    public Object measure(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();
        } finally {
            log.info("{} {}ms", pjp.getSignature(), (System.nanoTime() - start) / 1_000_000);
        }
    }
}

11-6. JPA · 트랜잭션 🔥

ORM 과 JPA

객체는 참조로 연결되고 테이블은 외래 키로 연결된다(패러다임 불일치). ORM 은 이 둘을 매핑해 SQL 을 대신 만들어 준다. JPA 는 자바 ORM 표준 명세, Hibernate 는 그 구현체, Spring Data JPA 는 리포지토리 구현을 자동 생성해 주는 추상화다.

방식장점단점
JPA (ORM)반복 SQL 제거, 객체 중심 설계, DB 방언 추상화복잡한 조회·통계에 불리, 내부 동작을 모르면 성능 사고
MyBatis (SQL 매퍼)SQL 을 직접 통제, 복잡한 쿼리·튜닝 용이반복 코드, DB 종속

영속성 컨텍스트

엔티티를 보관하는 1차 캐시이자 작업 단위. 보통 트랜잭션 하나와 수명을 같이한다.

기능내용
1차 캐시같은 트랜잭션에서 같은 ID 를 다시 조회하면 DB 에 가지 않음
동일성 보장같은 ID 는 같은 객체 (== 이 참)
쓰기 지연INSERT/UPDATE 를 모았다가 플러시 시점에 전송
변경 감지 (Dirty Checking)조회한 엔티티의 값을 바꾸면 커밋 시 자동으로 UPDATE. save() 를 다시 부를 필요가 없다
지연 로딩연관 객체를 실제로 쓸 때 조회 (프록시)
엔티티 상태설명
비영속 (new)영속성 컨텍스트와 무관
영속 (managed)관리되는 상태. 변경 감지 대상
준영속 (detached)관리되다가 분리됨. 변경해도 반영되지 않음
삭제 (removed)삭제 예약

N+1 문제

주문 목록 1번 조회 + 각 주문의 회원을 조회하는 쿼리 N번.

List<Order> orders = orderRepository.findAll();        // 쿼리 1번
for (Order o : orders) {
    o.getMember().getName();                           // 주문마다 쿼리 1번씩 → N번
}
해결방법주의
페치 조인select o from Order o join fetch o.member컬렉션 페치 조인 + 페이징은 메모리에서 처리되어 위험
@EntityGraph애너테이션으로 함께 조회할 연관 지정
배치 크기default_batch_fetch_size → 연관을 IN 절로 묶어 조회쿼리 수 1 + N → 1 + 1
DTO 직접 조회필요한 컬럼만 조인해 조회
  • 즉시 로딩(EAGER)이 해결책이 아니다. JPQL 은 여전히 N+1 을 일으키고, 필요 없는 연관까지 항상 끌려온다. 모든 연관은 지연 로딩(LAZY) 으로 두고 필요한 곳에서만 페치 조인한다.

@Transactional

AOP 프록시가 메서드 시작 전에 트랜잭션을 열고, 정상 종료 시 커밋, 예외 시 롤백한다.

전파 속성기존 트랜잭션이 있으면없으면
REQUIRED (기본)참여새로 시작
REQUIRES_NEW기존을 보류하고 새로 시작 (독립 커밋·롤백)새로 시작
SUPPORTS참여트랜잭션 없이 실행
MANDATORY참여예외
NOT_SUPPORTED보류하고 트랜잭션 없이 실행트랜잭션 없이 실행
NEVER예외트랜잭션 없이 실행
NESTED세이브포인트로 중첩새로 시작

자주 틀리는 것

함정설명
롤백 규칙기본은 RuntimeException 과 Error 에만 롤백. 체크 예외는 커밋된다 → rollbackFor 지정
자기 호출같은 클래스의 @Transactional 메서드를 내부에서 부르면 적용 안 됨
private · final 메서드프록시가 가로챌 수 없어 적용 안 됨
예외를 삼킴try-catch 로 잡고 던지지 않으면 롤백되지 않음
REQUIRED 안쪽에서 예외안쪽이 롤백 표시를 하면 바깥에서 예외를 잡아도 전체가 롤백 (UnexpectedRollbackException)
긴 트랜잭션트랜잭션 안에서 외부 API 를 호출하면 그동안 DB 커넥션과 락을 붙잡는다
  • @Transactional(readOnly = true): 변경 감지용 스냅샷을 만들지 않고 플러시를 생략해 조회가 가벼워지며, 읽기 전용 복제본으로 보내는 기준으로도 쓴다.
  • 격리 수준과 전파는 다른 개념이다. 격리는 → 격리 수준

커넥션 풀

DB 연결을 맺는 일(TCP + 인증)은 비싸다. → 미리 맺어 둔 연결을 빌려 쓰고 반납한다(HikariCP).

  • 풀이 너무 작으면 대기, 너무 크면 DB 가 문맥 교환·메모리로 느려진다. 풀 크기를 키우는 것이 답이 아닌 경우가 많다 — 느린 쿼리와 긴 트랜잭션이 원인이다.
  • 커넥션을 얻지 못하면 타임아웃 후 예외. 스레드 풀 크기 > 커넥션 풀 크기 이므로 DB 가 느려지면 요청 스레드가 줄줄이 대기한다.

멱등성

네트워크에서는 "요청이 처리되었는지 모르는" 상황이 반드시 생긴다(응답 유실, 타임아웃). 그래서 재시도는 필수이고, 재시도가 안전하려면 멱등해야 한다.

기법내용
멱등 키요청마다 고유 키. 처리 결과를 키와 함께 저장하고 재요청에는 저장된 결과를 반환
유일 제약(주문 ID, 결제 유형) 같은 자연스러운 유일성으로 중복 삽입 차단
상태 기계"결제 대기 → 결제 완료" 전이는 한 번만 허용. 이미 완료면 무시
절대값 갱신"잔액을 100 줄여라"(비멱등) 대신 "거래 #123 을 반영하라"
  • 화면에서 버튼을 비활성화하는 것은 사용성 개선일 뿐 중복 방지 수단이 아니다. 서버에서 막아야 한다.
