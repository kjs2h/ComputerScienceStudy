2-1. OSI 7계층 & TCP/IP 🔥 ✍️

왜 계층으로 나누는가?

통신이라는 복잡한 문제를 독립적인 단계로 분할하기 위해. 각 계층은 인접 계층과의 인터페이스만 지키면 되므로, 한 계층의 구현이 바뀌어도 다른 계층에 영향이 없다(모듈화, 캡슐화). 문제 발생 시 해당 계층만 조사하면 되어 문제 해결도 쉬워진다.

2-3. TCP 3-way / 4-way Handshake 🔥 🧮 ✍️

3-way Handshake (연결 수립)

   Client                                Server
     │                                     │  (LISTEN)
     │ ──── ① SYN, seq = x ──────────────► │
     │ (SYN_SENT)                          │  (SYN_RECEIVED)
     │                                     │
     │ ◄─── ② SYN + ACK, seq = y, ack = x+1 │
     │ (ESTABLISHED)                       │
     │                                     │
     │ ──── ③ ACK, ack = y+1 ────────────► │
     │                                     │  (ESTABLISHED)

왜 3번인가? (2-way로는 안 되는 이유) — 서술 필수

통신은 양방향이므로 양쪽 모두의 송신 능력과 수신 능력을 상호 확인해야 한다. - ①로 서버는 클라이언트의 송신 능력을 확인 - ②로 클라이언트는 서버의 송수신 능력을 확인 - ③이 있어야 서버가 클라이언트의 수신 능력을 확인할 수 있다

또한 지연 도착한 오래된 중복 SYN(delayed duplicate) 으로 인해 엉뚱한 연결이 열리는 것을 막고, 초기 시퀀스 번호(ISN)를 양방향으로 교환하기 위해서다.

↗ 부록 A · 빈칸 채우기

4-way Handshake (연결 종료)

   Client                                Server
     │ ──── ① FIN ────────────────────►    │
     │ (FIN_WAIT_1)                        │  (CLOSE_WAIT)
     │ ◄─── ② ACK ──────────────────────   │
     │ (FIN_WAIT_2)                        │  ← 서버가 남은 데이터를 마저 전송
     │ ◄─── ③ FIN ──────────────────────   │  (LAST_ACK)
     │ (TIME_WAIT)                         │
     │ ──── ④ ACK ────────────────────►    │  (CLOSED)
     │ (일정 시간 대기 후 CLOSED)             │

왜 연결은 4번인가? 연결 수립 시엔 서버의 SYN과 ACK를 하나의 세그먼트로 합칠 수 있지만, 종료 시엔 클라이언트가 FIN을 보내도 서버는 아직 보낼 데이터가 남아있을 수 있다. 그래서 ACK를 먼저 보내 "종료 요청은 받았다"고 알린 뒤, 데이터를 다 보내고 나서 별도로 FIN을 보낸다. → Half-Close 상태가 존재하기 때문.

TIME_WAIT 상태가 필요한 이유 (2가지) ⭐ 1. 마지막 ACK가 유실될 경우 서버가 FIN을 재전송하므로, 이에 응답하기 위해 대기해야 한다 2. 이전 연결의 지연된 패킷이 같은 포트를 재사용한 새 연결에 섞여 들어오는 것을 방지

2-4. 흐름 제어 vs 혼잡 제어 🔥

흐름 제어 (Flow Control) 혼잡 제어 (Congestion Control)
목적 수신 측의 버퍼 오버플로 방지 네트워크(라우터)의 과부하 방지
문제 상황 송신자가 수신자보다 빠름 전체 트래픽이 네트워크 용량 초과
제어 대상 송신자 ↔ 수신자 (End-to-End) 송신자 ↔ 네트워크 전체
사용 윈도우 rwnd (수신 윈도우, 수신자가 알려줌) cwnd (혼잡 윈도우, 송신자가 추정)
기법 Stop-and-Wait, Sliding Window Slow Start, Congestion Avoidance, Fast Retransmit/Recovery 
실제 전송 윈도우 = min(rwnd, cwnd)   ← 둘 중 작은 값

흐름 제어 기법 ⭐

  • Stop-and-Wait: 하나 보내고 ACK를 기다림. 단순하지만 매우 비효율적
  • Sliding Window: ACK를 기다리지 않고 윈도우 크기만큼 연속 전송. 수신자가 rwnd로 윈도우 크기를 통보
  • Silly Window Syndrome: 수신 버퍼가 조금씩만 비어 아주 작은 윈도우가 계속 광고되어 효율이 급락하는 현상 → Nagle 알고리즘(송신 측), Clark 방법 / 지연 ACK(수신 측)로 해결

답: 3중 중복 ACK(3 Duplicate ACK) 를 수신했기 때문이다.

수신자가 순서에 맞지 않는 세그먼트를 받으면, 기대하는 세그먼트 번호로 중복 ACK를 계속 보낸다. 송신자가 동일한 ACK를 3번 연속(총 4번) 받으면 특정 세그먼트만 유실되었다고 판단한다. 이때 타임아웃을 기다리지 않고 즉시 재전송하는 것이 빠른 재전송(Fast Retransmit) 이고, 이어서 cwnd를 1로 떨어뜨리지 않고 절반으로만 줄여 혼잡 회피 단계부터 재개하는 것이 빠른 회복(Fast Recovery) 이다.

핵심 논리: 중복 ACK가 온다는 것은 뒤따르는 세그먼트들이 여전히 수신자에게 도착하고 있다는 뜻이므로, 네트워크가 완전히 막힌 것은 아니다. 따라서 타임아웃(완전 두절)보다 가볍게 대응하는 것이다.

🔥 타임아웃 vs 3중 중복 ACK — 반드시 구별

혼잡 감지 방법 심각도 판단 cwnd 처리 이후 단계
3중 중복 ACK 가벼운 혼잡 (패킷은 흐르고 있음) 1/2로 감소 혼잡 회피부터 재개 (Fast Recovery)
타임아웃(Timeout) 심각한 혼잡 (연결 두절 수준) 1로 초기화 슬로 스타트부터 재시작

TCP Tahoe vs Reno ⭐: Tahoe는 두 경우 모두 cwnd를 1로 떨어뜨린다. Reno는 3중 중복 ACK 시 1/2로만 줄인다(Fast Recovery 도입). 그래프에서 1/2로 줄어드는 구간이 있으면 Reno다.

🔥 사설 네트워크의 외부 통신 구성 & NAT

구성 설명

[PC 1] 192.168.0.2 ┐
[PC 2] 192.168.0.3 ├─► [공유기/라우터]  ─── 인터넷 ───► [외부 서버]
[PC 3] 192.168.0.4 ┘   내부: 192.168.0.1
                        외부: 203.0.113.10 (공인 IP)
                        └ NAT / NAPT(PAT) 수행
  1. 각 PC는 공유기의 DHCP 서버 기능을 통해 사설 IP를 할당받는다
  2. PC가 외부로 패킷을 보내면 기본 게이트웨이(공유기)로 전달된다
  3. 공유기는 NAT(Network Address Translation) 를 수행하여, 패킷의 출발지 IP를 사설 IP → 공인 IP로 변환한다. 이때 출발지 포트 번호도 함께 고유한 값으로 변환하여 NAT 테이블에 기록한다 (NAPT / PAT, IP 마스커레이딩)
  4. 외부 서버는 공인 IP로 응답을 보낸다
  5. 공유기는 NAT 테이블의 포트 번호를 조회하여 어느 내부 PC의 응답인지 식별하고, 목적지 주소를 원래 사설 IP로 되돌려 전달한다

핵심: 사설 IP는 여러 대인데 공인 IP는 하나다. 무엇으로 구별하는가? → 포트 번호. 이걸 쓰지 않으면 감점.

사설 IP를 구분해서 얻는 이점

이점 설명
① IPv4 주소 고갈 완화 IPv4는 32비트로 약 43억 개뿐이다. 하나의 공인 IP로 수백 대의 내부 장비가 통신할 수 있어 주소 절약 효과가 크다
② 보안 향상 사설 IP는 인터넷에서 라우팅되지 않으므로 외부에서 내부 호스트로 직접 접근이 불가능하다. 자연스러운 방화벽 효과
③ 내부 네트워크 구성의 자율성 공인 IP를 새로 할당받지 않고도 내부에서 자유롭게 IP를 배정·재구성할 수 있다. ISP 변경 시에도 내부 구성 변경 불필요
④ 주소 중복 사용 가능 서로 다른 조직이 동일한 사설 대역(192.168.0.x)을 각자 쓸 수 있다

NAT의 단점 (가점 요소): 종단 간(End-to-End) 연결성이 깨져 외부에서 내부로 먼저 연결을 시도하는 서비스(P2P, 서버 운영)가 어렵다 → 포트 포워딩, STUN/TURN 등 별도 기법 필요

2-6. ARP / RARP 🔥

등장 배경

IP 주소는 논리 주소(3계층), MAC 주소는 물리 주소(2계층)다. 실제로 같은 LAN 안에서 프레임을 전달하려면 MAC 주소가 반드시 필요하다. 그런데 상위 계층은 IP 주소만 알고 있다. → IP ↔ MAC 변환 프로토콜이 필요하다.

ARP (Address Resolution Protocol)

  • 정의: IP 주소를 이용해 해당 호스트의 MAC 주소를 알아내는 프로토콜
  • 필요성: 데이터링크 계층에서 프레임을 전송하려면 목적지 MAC 주소가 필요한데, 상위 계층은 IP 주소만 가지고 있다. 이 둘을 연결해 주어야 실제 전송이 가능하다.
  • 동작: 1. 먼저 자신의 ARP 캐시 테이블을 조회. 있으면 그대로 사용 2. 없으면 ARP Request를 브로드캐스트 (LAN의 모든 호스트에게 "이 IP 가진 사람 MAC 알려줘") 3. 해당 IP를 가진 호스트만 ARP Reply를 유니캐스트로 응답 4. 받은 정보를 ARP 캐시 테이블에 저장 (일정 시간 후 만료)

왜 Request는 브로드캐스트이고 Reply는 유니캐스트인가? 요청 시점엔 누구에게 물어야 할지 모르므로 전체에게 물을 수밖에 없다. 응답 시점엔 요청 패킷 안에 요청자의 IP와 MAC이 이미 담겨 있으므로 그 대상에게만 직접 보내면 된다. (그림의 핵심)

RARP (Reverse ARP)

  • 정의: MAC 주소를 이용해 자신의 IP 주소를 알아내는 프로토콜 (ARP의 반대)
  • 필요성: 디스크가 없는(diskless) 워크스테이션처럼 자신의 IP 주소를 저장할 수단이 없는 장비가, 부팅 시 자신의 MAC 주소를 근거로 RARP 서버에게 IP를 받아오기 위해 필요하다.
  • 동작: 호스트가 RARP Request를 브로드캐스트 → RARP 서버가 미리 등록된 MAC-IP 매핑 표를 조회 → RARP Reply를 유니캐스트로 응답
  • 현재: 기능이 제한적(IP만 알려줌)이어서 BOOTP를 거쳐 DHCP로 대체되었다. DHCP는 IP뿐 아니라 서브넷 마스크, 게이트웨이, DNS 서버 주소까지 알려준다.

2-8. DNS (Domain Name System) ⭐ ✍️

정의

사람이 읽기 쉬운 도메인 이름을 IP 주소로 변환해 주는, 계층적·분산적 데이터베이스 시스템.

왜 분산 구조인가? 단일 서버로 관리하면 (1) 단일 실패 지점(SPOF), (2) 트래픽 집중, (3) 물리적 거리로 인한 지연, (4) 유지보수 불가능 — 이 네 가지 문제가 생긴다.

계층 구조

             Root DNS 서버 (.)
                    │
      ┌─────────────┼─────────────┐
   TLD(.com)     TLD(.kr)      TLD(.org)      ← Top Level Domain
      │
  Authoritative DNS 서버 (example.com)         ← 실제 레코드 보유
  • Local DNS 서버(리졸버): 사용자에게 가장 가까운 DNS. 캐싱을 담당한다.

↗ 요약 페이지 · DNS 레코드 타입 (3가지 이상 서술)

✍️ 재귀적 질의 vs 반복적 질의 (흐름도)

재귀적 질의 (Recursive Query) — "네가 알아서 다 찾아서 답만 줘"

요청 호스트 ─①→ Local DNS ─②→ Root DNS
                              ─③→ TLD DNS
                              ─④→ Authoritative DNS
                              ◄⑤─ (IP 응답)
                     ◄⑥─ TLD가 전달
            ◄⑦─ Root가 전달
요청 호스트 ◄⑧─ Local DNS

→ 질의를 받은 서버가 대신 다음 서버에 물어보고, 최종 답을 받아 되돌려 준다. 응답이 왔던 경로를 그대로 역순으로 돌아온다. 상위 서버의 부하가 크다.

반복적 질의 (Iterative Query) — "네가 아는 데까지만 알려줘, 나머진 내가 물어볼게"

요청 호스트 ─①→ Local DNS ─②→ Root DNS
                            ◄③─ "TLD 주소는 여기"
                            ─④→ TLD DNS
                            ◄⑤─ "Authoritative 주소는 여기"
                            ─⑥→ Authoritative DNS
                            ◄⑦─ (IP 응답)
요청 호스트 ◄⑧─ Local DNS

→ 각 서버는 "다음에 물어볼 서버 주소"만 알려주고, Local DNS가 직접 순차적으로 질의한다. 상위 서버의 부하가 적어 실제 인터넷에서는 이 방식이 주로 쓰인다.

정리: 요청 호스트 ↔ Local DNS 구간은 재귀적, Local DNS ↔ 상위 서버 구간은 반복적인 것이 일반적인 실제 구성이다.

Blocking Non-blocking

4가지 조합

조합 예시
Blocking + Sync 일반적인 파일 읽기 read() — 기다렸다가 결과 받음

2-10. 라우팅 테이블 · 라우팅 프로토콜 🔥 🧮

라우팅 테이블 해석 — 최장 접두사 일치 (Longest Prefix Match) 🧮

netstat -rn 출력의 각 행: Destination(목적지 네트워크) / Gateway(다음 홉) / Genmask(마스크) / Flags / Interface

판정 절차 (목적지 IP마다)
① 목적지 IP AND Genmask  == Destination  인 행을 모두 찾는다
② 여러 행이 맞으면 → 마스크가 가장 긴(1이 가장 많은 = 가장 구체적인) 행 선택
③ 하나도 없으면 → 0.0.0.0 / 0.0.0.0 (기본 경로) → 기본 게이트웨이로 보냄

마스크 범위 계산 예
  255.255.255.255 (/32) → 그 호스트 1개만        (Flag H = Host 경로)
  (설명용 예) 255.255.255.248 (/29) → 8개 블록: 172.16.0.16 ~ 172.16.0.23
  (설명용 예) 255.255.128.0   (/17) → 3번째 옥텟 128단위: 172.16.128.0 ~ 172.16.255.255
Flag 의미
U Up — 경로 사용 가능
G Gateway — 직접 연결이 아니라 게이트웨이(라우터)를 경유
H Host — 목적지가 네트워크가 아니라 단일 호스트(/32)

⚠️ 함정: 블록 크기 = 256 − 그 옥텟의 마스크 값. 마스크 128이면 128단위, 192면 64단위, 248이면 8단위. 목적지 IP가 그 블록 범위에 드는지로 판정하고, 여러 행이 맞으면 더 긴 마스크가 이긴다.

기본 게이트웨이(Default Gateway)의 역할 🔥

라우팅 테이블에 일치하는 항목이 없는 모든 패킷을 보내는 출구. 호스트가 모든 목적지 경로를 알 수 없으므로, 모르는 목적지는 기본 게이트웨이(보통 외부와 연결된 라우터)에 맡겨 다른 네트워크(인터넷)로 나가는 관문 역할을 한다. 라우팅 테이블 크기를 줄이는 효과도 있다.

2-12. IPv4 → IPv6 전환 기법 🔥

등장 배경: IPv4(32비트, 약 43억 개) 주소 고갈 → IPv6(128비트). 그러나 두 프로토콜은 헤더 형식이 달라 직접 통신 불가하고, 전 세계 망을 한 번에 바꿀 수 없다 → 공존 기간의 전환 기법이 필요하다.

기법 동작 쓰는 상황
이중 스택 (Dual Stack) 호스트·라우터에 IPv4와 IPv6 스택을 모두 탑재, 상대에 맞춰 선택 (DNS가 AAAA 주면 IPv6, A 주면 IPv4) 장비가 둘 다 지원 가능할 때. 가장 기본
터널링 (Tunneling) IPv6 패킷을 IPv4 패킷에 통째로 캡슐화해 IPv4 구간을 통과, 반대편에서 꺼냄 (6to4, ISATAP) 양 끝은 IPv6, 가운데 구간이 IPv4
헤더 변환 (Header Translation) 중간 장비(NAT64 등)가 IPv6 헤더 ↔ IPv4 헤더를 직접 변환 한쪽은 IPv6만, 다른 쪽은 IPv4만 지원 
[터널링]   IPv6 ─▶ [IPv4 헤더 | IPv6 헤더 | 데이터] ─(IPv4 망)─▶ 역캡슐화 ─▶ IPv6
[헤더 변환] IPv6 전용 ─▶ [IPv6|데이터] ─▶ 변환기 ─▶ [IPv4|데이터] ─▶ IPv4 전용
  • 헤더 변환의 단점: IPv6에만 있는 필드(흐름 레이블 등)는 대응 필드가 없어 정보가 손실될 수 있음 → 다른 방법이 없을 때 쓰는 최후 수단
  • 터널링은 VPN 터널링(3-1)과 같은 캡슐화 원리
IPv4 vs IPv6 ⭐ IPv4 IPv6
주소 길이 32비트 128비트
헤더 가변(20~60B), 체크섬 있음 고정 40B, 체크섬 제거(처리 단순화)
주소 유형 유니·멀티·브로드캐스트 유니·멀티·애니캐스트 (브로드캐스트 없음)
보안 IPsec 선택 IPsec 기본 지원

등장 배경: 여러 노드가 하나의 채널을 공유하면 신호가 섞인다 → 매체 접근 제어(MAC)가 필요.

CDMA 원리 — 직교(Orthogonal) 칩 순열

각 노드의 칩 순열은 서로 내적하면 0, 자기 자신과 내적하면 칩 수 m이 되도록 설계된다(Walsh 코드).

c1 = (+1, +1, +1, +1)     c1·c2 = 1 − 1 + 1 − 1 = 0   ← 서로 다르면 0
c2 = (+1, −1, +1, −1)     c2·c2 = 1 + 1 + 1 + 1 = 4   ← 자기 자신이면 m
c3 = (+1, +1, −1, −1)
c4 = (+1, −1, −1, +1)

→ 여러 신호를 더해서 보내도, 받는 쪽에서 원하는 노드의 칩으로 내적하면 다른 노드 신호는 0으로 소거되고 그 노드의 데이터만 남는다.

CDMA 계산 절차 🧮

1. 비트 코딩   : 0 → −1,  1 → +1,  보내지 않음(idle) → 0
2. 부호화      : 출력 신호 = d × c   (칩마다 곱)
3. 공통 채널   : 모든 노드 출력을 칩 위치별로 더함  Σ dᵢ·cᵢ
4. 복호화      : (채널 신호 · cₖ) ÷ m
                 → +1이면 비트 1, −1이면 비트 0, 0이면 그 노드는 송신 안 함

예) 노드1·2가 0, 노드3 idle, 노드4가 1
  출력: 노드1 (−1,−1,−1,−1)  노드2 (−1,+1,−1,+1)  노드3 (0,0,0,0)  노드4 (+1,−1,−1,+1)
  채널: (−1, −1, −3, +1)
  c2로 복호화: (−1)(+1)+(−1)(−1)+(−3)(+1)+(+1)(−1) = −4 → −4÷4 = −1 → 비트 0  ✓
  c4로 검증  : (−1)(+1)+(−1)(−1)+(−3)(−1)+(+1)(+1) = 4 → +1 → 비트 1  ✓
  c3로 검증  : −1 −1 +3 −1 = 0 → 노드3은 송신하지 않음  ✓

⚠️ 함정: ① 내적 뒤 칩 수 m으로 나누기를 빠뜨리지 말 것 ② idle 노드는 −1이 아니라 0 ③ 답을 낸 뒤 다른 노드로 복호화해 원 데이터와 대조하면 검산이 된다.

2-14. HTTP — 버전 · 메서드 · 상태 코드 · 캐시 🔥

HTTP의 두 가지 성질

  • 무상태(Stateless): 서버가 이전 요청을 기억하지 않는다. → 서버를 늘리기 쉽다(확장성). 대신 로그인 같은 상태는 쿠키·세션·토큰으로 따로 유지한다.
  • 비연결(Connectionless): 요청-응답 후 연결을 끊는 것이 기본. → HTTP/1.1부터 Keep-Alive(지속 연결) 가 기본이 되어 연결을 재사용한다.

2-16. 주소창에 URL 을 입력하면 일어나는 일 🔥

면접 단골이자 네트워크 전 범위를 한 번에 훑는 문제다. 계층을 따라 내려갔다가 올라오는 순서로 답한다.

  1. URL 해석: 스킴(https), 호스트, 포트(443), 경로를 분리. HSTS 목록에 있으면 강제로 HTTPS.
  2. DNS 조회: 브라우저 캐시 → OS 캐시(hosts) → 로컬 DNS 서버 → (없으면) 루트 → TLD → 권한 네임 서버 순으로 재귀/반복 질의. → DNS
  3. 경로 결정: 목적지가 같은 서브넷이 아니면 기본 게이트웨이로 보낸다. 게이트웨이의 MAC 주소는 ARP 로 알아낸다. → ARP
  4. TCP 연결: 3-way Handshake. → Handshake
  5. TLS 핸드셰이크: 인증서 검증, 키 합의.
  6. HTTP 요청 전송: 요청은 사설 IP → NAT → 공인 IP 로 바뀌어 인터넷을 지나고, 라우터들이 최장 접두사 일치로 전달한다.
  7. 서버 측: CDN/로드 밸런서 → 웹 서버(리버스 프록시) → 애플리케이션 서버 → 캐시/DB.
  8. HTTP 응답: 상태 코드, 헤더, 본문(HTML).
  9. 렌더링: HTML 파싱 → DOM, CSS 파싱 → CSSOM, 둘을 합쳐 렌더 트리 → 레이아웃 → 페인트. 도중에 만난 CSS·JS·이미지는 추가 요청한다.
  10. 연결 유지/종료: Keep-Alive 로 재사용하다가 4-way Handshake 로 종료.

답변 요령: 질문자가 깊이 들어가길 원하는 지점(DNS, TCP, TLS, 렌더링)을 스스로 하나 골라 한 단계 더 설명하면 좋은 평가를 받는다.

CDN (Content Delivery Network)

사용자와 지리적으로 가까운 엣지 서버에 콘텐츠 사본을 두어 지연을 줄이고 원본 서버 부하를 덜어 준다.

  • 동작: DNS 가 사용자와 가까운 엣지 IP 를 응답 → 엣지에 캐시가 있으면 바로 응답(Hit), 없으면 원본에서 가져와 저장(Miss).
  • 대상: 이미지·영상·JS·CSS 같은 정적 콘텐츠가 기본. 동적 콘텐츠도 경로 최적화·TLS 종료로 이득을 본다.
  • 부가 효과: 트래픽을 넓게 흡수하므로 DDoS 완화에 쓰인다.
  • 주의: 배포 후에도 옛 파일이 보이는 문제 → 파일 이름에 해시를 붙이거나(캐시 버스팅) 무효화(purge)한다.

예제. 데이터 1101011011, 생성 다항식 G(x) = x⁴ + x + 1 (10011) 일 때 전송 프레임은?

풀이
  1. 생성 다항식이 5비트이므로 데이터 뒤에 0 을 4개 붙인다 → 11010110110000
  2. 10011 로 모듈로-2 나눗셈(뺄셈 대신 XOR)을 한다.
  3. 나머지 = 1110
  4. 전송 프레임 = 데이터 + 나머지 = 11010110111110
  5. 수신 측은 받은 프레임을 10011 로 나눠 나머지가 0 이면 오류 없음으로 판단한다.

모듈로-2 나눗셈 규칙: 현재 맨 앞 비트가 1 이면 제수와 XOR, 0 이면 00000 과 XOR(그대로) 하고 다음 비트를 내린다.
